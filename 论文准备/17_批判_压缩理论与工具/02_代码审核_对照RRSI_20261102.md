# 02 代码审核 —— 对照 RRSI 逐模块、逐函数

> **一句话结论：我们不是"写得臃肿"，是"每个环节都比 RRSI 细一倍"。**
> 函数平均长度几乎一样（15.2 vs 15.7 行），真死码只有 12 行。
> 差距集中在两块：**config（6.1 倍）与 components（5.7 倍）** —— 都把"能改"做到了"改得准"。

## 二、先排除两个常见解释

### 2.1 不是"函数写得胖"

| 指标 | RRSI（全部） | 我们 |
|---|---|---|
| 函数数 | 290 | **680（2.3×）** |
| 平均行数 | 15.7 | **15.2** |
| 中位行数 | 8 | **9** |
| ≥30 行长函数 | 41（14%） | 82（12%） |
| ≤3 行轻函数 | 85（29%） | 152（22%） |

**函数粒度几乎完全相同。** 我们不是把函数写长了，是**写了更多个同样大小的函数**。

⇒ 问题在"数量"，不在"单体"。

### 2.2 不是"堆了死代码"

模块级真死函数（零引用 + 非 Protocol + 测试也不用）：**3 个 / 12 行**。

`ghost` 的 137 个"零引用函数"里，134 个是**类方法**，其中绝大多数是有意的能力预留：
`sandbox_openhands.replay`（非反馈轮的解药）、`adapters.*.stats`（Protocol 实现）、
`domain.*` 的 calibrate/coupling/online 一族（论文验收项）。

⇒ **删死码这条路，在这个仓库上已经走到头（12 行）。**

### 三个结论

1. **8 个阶段是"1.5–2.4 倍"的均匀放大** —— 这不是某处写崩了，是**每个环节都多做了校验与边界**。
   RRSI 是研究原型（一个 critic 147 行 6 类拒），我们是工具（critic 216 行 8 条规则 + 值域 + 接线 + 删除安全）。
2. **两块异常放大**：`components` 5.7×、`config` 6.2×。
   这两块干的是"**精确定位可编辑单元**"与"**精确改文件且能回退**"——RRSI 只要求"能改"，
   我们要"改得准、改得可查、改得回退"，代价就是 5–6 倍。
3. **有一块是 0**：`schedule`（退火预算 b_t）。这正是批判文档缺陷 4 —— **RRSI 有的我们没有**。

⇒ **"功能比它多不了多少"这个判断要修正**：我们多了 K 度量（804）、线上放量（231）、
守卫（520）、样本池/回归/报告（~600）≈ **2,150 行 RRSI 完全没有的功能**；
另有 8 个阶段各多一倍（约 +2,800 行）来自"更细的校验"。
剩下的才是可能的冗余。

## 四、冗余审计（只认能拿出证据的）

| 类型 | 数量 | 行数 | 判定 |
|---|---|---|---|
| 模块级真死函数 | 3 | **12** | ✅ 已删（本轮） |
| 可内联的单调用小函数 | 32 | 827 | ⚠ 其中 **12 个是 `cli.cmd_*`（约 500 行）不能内联** —— 它们是 `set_defaults(func=…)` 的动态分发点，静态调用图看着"只引用 1 次"，内联即废 |

**唯一能上四位数（raw 行）的只有最后一行。** 但它不是"两个都留、慢慢接"，而是**只留一个**：

| | `run_m0_round`（旧） | `orchestrator.evolve_round`（新） |
|---|---|---|
| 跑基线 | ✅ `res.full` | ✅ `stage1(…, skill_text)` @251 |
| 跑改后版本 | ✅ `res.short` | ✅ `stage1(…, candidate_text)` @345 |
| 算 ΔS | ✅ | ✅ `delta_pp` |
| **调 gate 下结论** | ✅ | ❌ 只报 `caveat` 不判 |

**给 `orchestrator` 补一次 `gate()` 调用与三张表，`run_m0` 退役**——因为它改动更有依据、可逐卡审退、还多一层轨迹侦查。

## 五、本轮改动（对照修改前后）

| 项 | 修改前 | 修改后 |
|---|---|---|
| `domain/evaluate.py` | 含 `delta_s` / `delta_c` / `delta_k` 三个零引用函数 | 删除（`gate._rel()` 已实现同样逻辑，且是唯一实际使用处） |
| `domain/__init__.py` | re-export 含上述三个名字 | 同步移除（`__all__` 是导出契约，不同步会炸 56 个测试模块） |
| 非测试 SLOC | 10,232 | **10,222（−10）** |
| 公开符号 | 344 | **341（−3）** |
| K（gzip −9） | 222,450 | **222,298（−152）** |
| 测试 | 883 | **883 passed** |

**踩到的坑（值得记）**：删函数后 56 个测试模块 import 失败 —— 因为 `src/domain/__init__.py`
把它们 re-export 了。**删公共符号必须同时清 `__init__.py` 的 import 与 `__all__`**，
否则静态扫描看着"零引用"，运行时却是全包依赖。

## 七、一句话回答"为什么不简洁"

**因为我们做的是工具，RRSI 做的是原型。**

原型只需要证明"这个机制有效"，所以 critic 147 行、components 108 行、config 97 行就够；
工具要保证"改得准、改得可查、改得回退、别人能复现"，同样三个环节就得 216 / 612 / 605 行。

**但有一条是实打实的落后：我们没有 `schedule.py`（退火预算 54 行）。**
RRSI 用 54 行做的事，我们 0 行——这不是"更简洁"，是"漏了"。
