# 一、实验设计

## 1.1 用的哪篇的方法

**SHarP（`2610.04178`）的单模块消融**：把每个单元独立关掉，跑评测，看分数是否掉。

SHarP 原文的成本是 `1 + m` 次评测（全量 1 次 + 每个模块各 1 次），不是 `2^m` 种组合——这是它敢在 27 个模块上做的原因。

## 1.2 移植到本项目的对应关系

| SHarP | 本项目 |
|---|---|
| 关掉一个工具 / 机制 | 把一个顶层函数替换成 `raise NotImplementedError` |
| 跑任务评测集，看通过率 | 跑 pytest，看测试是否仍全绿 |
| 27 个模块 / 4 个 harness | 9 个函数 / 3 个测试文件（41 个测试） |

## 1.3 目标与测试范围

- 目标：`src/domain/code_split.py`，202 行 / 9 个顶层函数
- 测试：`test_code_split.py` + `test_d4_f1.py` + `test_sample_pool.py`（直接相关，41 个测试）
- 脚本：`skills/代码简化/scripts/ablation.py`（逐函数替换 → 跑 → 立刻按字节恢复）

# 三、那 2 个候选为什么不能删

## 3.1 调用链：都在生产路径上

```
simplify.py:244  →  verify_ood()  →  run_pristine_tests()
```

两个都在真实执行路径上，**不是死代码**。

## 3.2 为什么删了测试不挂

`simplify.py:242-249`：

```python
if ood_baseline is not None:
    try:
        from ..domain.code_split import make_split, verify_ood
        sp = make_split(root)
        res.ood = verify_ood(root, sp, baseline_passed=..., timeout=timeout)
    except Exception as exc:                          # noqa: BLE001
        res.ood = {"verdict": "ood-error", "detail": str(exc)[:200]}
```

两重保护，每一重都让"删坏"变得看不出来：

**① `if ood_baseline is not None`** —— 测试里从不传这个参数，所以测试根本进不来这段。**零覆盖**。

**② `except Exception`** —— 就算进来了，`ImportError`（`verify_ood` 被删）也会被捕获，退化成 `{"verdict": "ood-error"}`。**不抛异常、不报错。**

**叠起来的结果**：

| 场景 | 表现 |
|---|---|
| 删掉 `verify_ood` 后跑测试 | **41 全过** |
| 删掉后跑真实实验 | `res.ood = {"verdict": "ood-error"}`，实验照跑 |
| 真实后果 | **OOD 防泄漏检查永久失效，而且没人知道** |

**这比"删了挂掉"危险得多。** 挂掉会有人修，静默失效会一路带到论文数据里。

## 3.3 `except Exception` 本身就该修

`src/` 里生产代码有 **22 处 `except Exception`**。其中 `simplify.py` 有 5 处，至少两处会掩盖"代码坏了"：

| 位置 | 行为 | 风险 |
|---|---|---|
| `L110` | `return None` | 吞掉一切，调用方分不清"没数据"和"程序坏了" |
| `L247` | `res.ood = {"verdict":"ood-error"}` | **删掉 OOD 模块也不报错** |

**这是"删了看起来没事"的根源。** 不修它，任何基于"跑一遍看有没有报错"的判据都不可靠。

# 四、三个工程坑（都实测踩过）

## 4.1 换行符：`write_text` 会吞 CRLF

原文件是**混合换行符**：136 个 CRLF + 66 个纯 LF（8801 字节）。
`Path.read_text()` 做 universal newline 转换 → `Path.write_text()` 全写成 LF → **sha256 对不上，报"恢复失败"，但内容其实是好的**。

**修法**：`read_bytes()` 存原件，恢复时 `write_bytes(orig)`。判据改成字节相等，不是"语义相等"。

## 4.2 退出码：41 全过却 rc=1

```
.........................................  [100%]
[safe-delete][SAFE_DELETE_BULK_GUARD_ERROR] failed to acquire lock: EPERM ...
```

WorkBuddy 宿主的 safe-delete 钩子在 pytest 清理 basetemp 时抢锁失败，**污染退出码**。

`src/usecases/simplify.py:137` 的 docstring 早就记了这条，**我还是踩了一次**。

## 4.3 终端输出：summary 行也被吞

`-q` 模式下本该有 `41 passed in 0.52s`，实际**没有**——钩子把 summary 一起吞了。

所以"解析输出文本"也不可靠。

**修法（4.2 + 4.3 一起）**：用 pytest 内置的 `--junit-xml`。它是 pytest 自己写的文件，不受终端和退出码影响。

```python
ts = root.find("testsuite")
t, f, e = ts.get("tests"), ts.get("failures"), ts.get("errors")
```

# 五、这个实验真正证明了什么

## 5.1 `src/` 的可删量是 0，不是"没测出来"

三次独立测量的结果一致：

| 方法 | 结果 |
|---|---|
| 死代码检测（引用计数） | 11 候选 / 35 行 / **0.1%**，其中 10 条误报，真能删 8 行 |
| 逻辑冗余（AST 同构 + 模式） | 生产代码 2 组 29 行 + 模式 4 处 31 行 |
| **消融（本篇）** | **9 个函数 / 0 行**（2 个候选全是假阳性） |

**三种方法都指向同一个数：几十行。** 这不是巧合，是这类代码的固有性质——它是**分层设计出来的**，不是补丁喂大的。

## 5.2 为什么 SHarP 能删 24/27，我们不能

| | SHarP 的对象 | 我们的 `src/` |
|---|---|---|
| 代码怎么来的 | 被上游反复 patch 长出来的 | 按分层手写 |
| oracle | **任务通过率**（真实使用） | **单元测试**（作者想到的） |
| 冗余形态 | 功能重叠（4 个 harness 都能做同类任务） | 极少 |
| 结果 | 27 个剪 24 个，分数反涨 | 9 个剪 0 个 |

**第一行和第二行是因果，不是巧合。**

> **单元测试问的是"作者想到的路径还通不通"，任务通过率问的是"真实使用还通不通"。**
> 前者漏掉的，正好是"作者没想到要测"的那部分——而那部分恰恰是最容易被误删的。

## 5.3 对论文的方法论含义

**要做"消融 → 删减"，oracle 必须是真实任务，不能用单测。**

这意味着成本从"跑 41 个测试（0.5 秒）"变成"跑 30 题 × N 次实验（几十分钟）"。`1 + m` 次 = 10 个模块 × 30 题 × 4 rep = **1,200 trial**。

**这是必须付的代价。** 想省掉它，就会像这次的 2 个候选一样，删掉 OOD 检查还以为自己赚了 38 行。
