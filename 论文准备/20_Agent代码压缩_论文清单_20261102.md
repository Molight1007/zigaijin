## 〇、一句话结论

**"压缩"这件事被做成了四件不同的事，而且彼此不通气：**

| 大家压的是什么 | 代表 | 压完的收益记在谁账上 |
|---|---|---|
| 压**上下文**（喂给模型的 token） | LLMLingua / ACON / ACE | 推理成本 |
| 压**模块**（整个工具/指令/机制关掉） | SHarP / Cortex | 执行成本 + 少量分数 |
| 压**代码结构**（重构、去冗余） | CodeTaste / REFINE / SlopCodeBench | 可维护性 |
| 压**测试用例**（保 bug 的最小复现） | ddmin / Perses / HarnessMinimizer | 调试效率 |

**没有一篇把"源码描述长度"当成演化回路里的独立选择压力。** 最接近的 SHarP 也只是**事后一次性剪枝**，剪的判据是 token 成本，不是描述长度。

这个位子还空着——但比一个月前窄了（见 §10）。

## 二、族 0：直接剪 harness —— 最危险的两篇

这两篇是**唯一和我们在同一层动手**的工作。必须先看它们。

### 0.1 SHarP: Saliency-based Pruning of Agent Harnesses ★★★★★

| 项 | 内容 |
|---|---|
| arXiv | **2610.04178**（v1 2026-10-03） |
| 作者 | Xinyi Gao, Qiucheng Wu, Kaizhi Qian, Handong Zhao, Shiyu Chang, Yang Zhang |
| 做法 | 把工具/指令/支撑机制识别为**可单独关闭的模块**；对每个模块做**单模块消融**，测两个显著性——**性能显著性**（关掉后分数掉多少）与**效率显著性**（关掉后 token 省多少）；只做一轮消融就能排序，然后按两种策略剪（效率优先 / 性能优先） |
| 结果 | 4 个 harness 在各自验证集上：**全部保持可比性能，token 成本至少降 10%**；其中 2 个 harness **剪完分数还涨了** |
| 结论原话 | "我们研究的大多数 harness 高度冗余" |

**为什么它最危险**：它把"harness 有大量冗余"这件事**用实验坐实了**。这句话本来是我们要论证的前提，现在别人已经证了。

**但它留了三个空子，我们的增量必须落在这里：**

| SHarP 没有 | 说明 |
|---|---|
| **描述长度 K** | 它的剪枝判据是 **token 成本**（efficiency saliency），不是源码长度。压 token ≠ 压描述长度——一个模块可以零 token 却占两百行代码 |
| **演化回路内的接受准则** | 它是**训练完事后剪一刀**，不是每轮演化都带 K 约束。所以拦不住"越改越胖"这个过程本身，只能事后瘦身 |
| **行为等价回归** | 它是**整模块开关**，不涉及"改代码但行为不变"。我们做的 AST 级删减 + 三重门，是它没碰的粒度 |
| **OOD / 过拟合视角** | 全文只谈 performance × token cost，**不谈泛化**。这正是我们的第二维 |

> **一句话定位**：SHarP 回答"哪些模块可以关掉"，我们回答"这个改动值不值得留"。前者是**事后审计**，后者是**事前选择压力**。这个区别必须写清楚，否则会被说成"SHarP 换个指标"。

### 0.2 Cortex: Measurement-Gated Evolution and Pruning of Coding-Agent Skills and Rules ★★★★

| 项 | 内容 |
|---|---|
| arXiv | **2610.14216**（2026-10-09，单作者，独立研究者 Samuele Giampieri） |
| 对象 | Claude Code 的 harness = `CLAUDE.md` 项目文件 + skills（模型自选打开）+ rules（读匹配文件时自动加载） |
| 做法 | 把开发者每次纠正保存成**可回放任务** → 找出反复出现的纠正 → 一次只写一条 skill 或 rule → **带/不带各跑几次**，只有"整体净收益 + 没有任何单题明显变差"才留；**已有文本删除前也走同一套测试** |
| 关键约束 | 全程记录每段文本是否**真的到达过模型**；**模型从没用过的文本，既不新增也不删除** |
| 结果 | Haiku 4.5 上比"无 skills/rules"基线 **+55.0 个百分点**；rules（自动加载）贡献主要增益，skills 只有在"随任务涉及文件一起提供"时才有用，每轮都摆在面前的 skills 很少被打开 |
| **诚实之处** | 作者自己写清：强模型 Sonnet 5 上单轮 harness 增益很小；真实开源项目上"没找到可学的东西"；植入的有害规则**没能被识别**——"这证明 Cortex 不留没用的文本，不证明它能识别有害文本" |

**为什么值得重点读**：它做了一件我们该做但容易漏的事——**先证明"这段文本被使用过"再谈它有没有用**。这是"证据链"的完整形态。

**它还免费送了我们一个 δ**：同一个 harness、同一批任务、分两批 rollout，**相差 −3.3 个百分点（95% CI [−7.3, 0.0]）**。这是"同一版本重复评测的散布"的实测值，可以直接引用来支撑"δ 是测出来的，不是选的"。

**它的短板**：单作者、单模型、自制仓库（不是公开 benchmark）、样本量小。证据强度按 **B** 看待，不能当定论。

## 三、族 1：提示 / 上下文压缩 —— 方法最成熟，但压的不是"代码"

这一族论文最多、最成熟，但**压的对象是喂进去的 token，不是 harness 源码**。引用时千万别说错，否则一问"你压的和我压的不是一个东西"就崩。

### 1.1 LLMLingua 三连（这一族的基准线）

| 论文 | 编号 | 做法 | 关键数字 |
|---|---|---|---|
| **LLMLingua** | arXiv **2310.05736**，EMNLP 2023 | 小模型（GPT-2 small / LLaMA-7B）算每 token 的困惑度与互信息，删低信息量 token；预算控制的由粗到细 | **最高 20× 压缩**，性能损失最小 |
| **LongLLMLingua** | arXiv **2310.06839**，ACL 2024 | 问题感知 + 位置感知，专治长上下文"lost in the middle" | RAG **+21.4%**，只用 **1/4** token |
| **LLMLingua-2** | arXiv **2403.12968**，ACL 2024 Findings | 把压缩重构成**token 分类**任务，用 GPT-4 蒸馏训练 BERT 级编码器 | 比 LLMLingua **快 3–6×**，跨域更稳 |

**对我们的用法**：① 现成的压缩算子，可直接嵌进阶段 1 的审计模块；② 它输出的"token 重要性分布"是一种**比 gzip 更语义感知**的长度刻画。

**但**：它是**抽取式**的（保留原词面），删的是 token，不删结构。它不能告诉你"这五个 if-else 该合并成一个函数"。

### 1.2 软提示 / 学到的压缩（压到向量，人看不懂）

一族把上下文压成**连续向量**而非文字：**Gist tokens**（2304.08467）、**AutoCompressor**（2305.14788）、**ICAE**（2307.06945）、**xRAG**（2405.13792，压成一个 token）、**500xCompressor**（ACL 2025，6×–500×，保留 70–74% F1 / 77–84% EM）。

**对我们的价值：几乎没有，甚至是个反例。**
压成向量后人审计不了，而且多跳/算术推理会显著退化（中间步骤需要精确 token）。这恰好是我们主张"要**可审计的**压缩、K 要可复算"的反面教材。可以引一句，说明为什么我们不走这条路。

### 1.3 ACON：给长程 agent 压上下文 ★★★★

| 项 | 内容 |
|---|---|
| arXiv | **2510.00615**（v1 2025-10-01，v3 2026-06-01） |
| 作者 | Minki Kang 等（Microsoft） |
| 做法 | 不改模型权重，只**优化"压缩指南"这段自然语言**：拿"完整上下文成功、压缩后失败"的成对轨迹，让强模型分析失败原因，据此改指南；再把优化后的压缩器蒸馏进小模型降开销 |
| 结果 | 峰值 token **−26～54%**；小模型当长程 agent **最高 +46%**（AppWorld +32%、OfficeBench +20%） |

**⚠️ 它的负面结果极重要，别漏**（**2026-11-02 更正**：此处曾误写为"历史压缩几乎不省钱"，那是 v1 附录的说法；v3/ICML 版表 4 的实测是"省钱但变慢"）：

| AppWorld 端到端 | API 成本 | 延迟 |
|---|---|---|
| 不压缩 | $0.331 | 73.24s |
| ACON 压历史 | $0.285（**−13.9%**） | 87.68s（**+19.7%**） |
| ACON 压观察 | $0.272（**−17.8%**） | 101.92s（**+39.2%**） |

**这条对我们是警告**：如果我们把论文卖点写成"压缩能降成本"，会被这张表直接反驳——省 14–18% 的钱，代价是 20–39% 的延迟。
**正确的卖法**：K 降的是**结构冗余与可审计性**，不是账单。省钱是副产品，而且很可能被延迟抵消。

### 1.4 ACE：压缩的反面证据，必须能回答 ★★★★★

| 项 | 内容 |
|---|---|
| arXiv | **2510.04618**（ICLR 2026） |
| 作者 | Qizheng Zhang, Changran Hu 等（Stanford + SambaNova + UC Berkeley） |
| 诊断 | 现有上下文自适应有两个病：**brevity bias**（为了简洁丢掉领域细节）、**context collapse**（迭代重写导致知识逐轮侵蚀） |
| 那组致命数字 | AppWorld 第 60 步，上下文约 **18k token、准确率 66.7%**；模型做了一次"总结压缩"，剧本被削到 **122 token**，准确率掉到 **57.1%**——**比不压缩的基线还差** |
| 解法 | 不重写，只做**结构化增量更新**（delta）+ 确定性 grow-and-refine 合并去重；三角色分工：Generator 干活 / Reflector 提炼教训 / Curator 格式化成条目 |
| 结果 | agent +10.6%、金融 +8.6%；适配延迟比 GEPA **−86.9%** |

**这是我们最强的对手，也是最好的论据，取决于怎么用：**

- **当对手**：它证明"盲目追求短 = 自毁"。任何"以最短为目标"的主张都必须先跨过这一关。
- **当论据**：它恰好证明**"压缩需要一个不丢信息的表示"**——ACE 用"条目化 + 增量"解决，我们用"AST 级删减 + 行为等价回归 + 防御白名单"解决。**同一个病，两种药，我们是代码侧的那一种。**

**必引。而且必须在 intro 里就回应，不能等到 limitation。**

## 四、族 2：代码重构与简化 —— 离"代码"最近，但目标是可维护性不是长度

### 2.1 SlopCodeBench：把"agent 代码越写越烂"量化了 ★★★★★

| 项 | 内容 |
|---|---|
| arXiv | **2603.24755** |
| 作者 | Gabriel Orlanski 等（UW-Madison + WSU + MIT） |
| 做法 | 36 题 / 196 检查点，agent **反复扩展自己上一版的代码**（不是改人类仓库）；规格演进只规定外部行为，**内部结构完全留给 agent** |
| 两个度量 | **verbosity**（冗余/重复代码占比）、**structural erosion**（复杂度向少数函数集中） |
| 结果 | 15 个 agent，**没有一个端到端解出任何一题**，最好只过 **14.8%** 检查点；structural erosion 在 **77%** 的轨迹里上升，verbosity 在 **75.5%** 里上升；对比 473 个开源 Python 仓库，**agent 代码啰嗦 2.3×、侵蚀 2.0×**；人类仓库长期看是平的，agent 代码逐轮恶化 |
| 最扎心的一条 | **明确的质量提示能把初始 verbosity/erosion 降三分之一，但不改变恶化速率** |

> **版本提醒**：v1 是 20 题/93 检查点、2.2×、80%/89.8%；现行版是 36/196、2.3×、77%/75.5%。引用前确认版本，两套数字不能混用。

**对我们的价值 = 现成的"病"**。
我们要论证"harness 会越改越胖"，这篇给了**跨 15 个 agent、473 个仓库的实测**。而且它证明了"光靠提示写好点"没用——**必须有选择压力**。这正好是我们的药。

**它也是威胁**：`verbosity` 已经在被当指标测了。我们的 K 必须比"冗余代码占比"严格更强（可复算、区分内容来源、AST 级白名单豁免），否则会被说成"SlopCodeBench 的 verbosity 换个名字"。

### 2.2 CodeTaste：LLM 会不会重构？会做，但不会"选" ★★★

| 项 | 内容 |
|---|---|
| arXiv | **2603.04177**（2026-03） |
| 作者 | Alex Thillen, Niels Mündler, Veselin Raychev, Martin Vechev（ETH Zurich + LogicStar） |
| 做法 | 从大型多文件开源重构挖出 benchmark；评分 = 仓库测试套件（功能正确）+ 定制静态检查（用数据流推理验证"不该有的模式删了、该有的模式加了"） |
| 结论 | **给详细规格让它做，做得好；给一个改动区域让它自己找该重构什么，经常找不到人的选择**；"先提议再实施"能提升对齐度 |

**对我们的用法**：这是"压缩算子能不能自动发现重构机会"的直接证据。答案是**部分能**——这支持我们"算子分级、高风险算子要更严验证门"的设计。

### 2.3 REFINE：重构的"保持性"到底有多不可靠 ★★★

| 项 | 内容 |
|---|---|
| arXiv | **2608.23611** |
| 做法 | 多 agent 工作流：检测坏味道 → 规划 → 变换 → 验证 → 报告，每个候选都挂上"动机证据 + 验证结果 + 残留风险" |
| 关键发现 | 三个强模型的**重构风格差异很大**：GPT-5.5 改动紧凑、Gemini 3.1 **删除偏多**（净 LOC 降得多，但公开方法删除多）、Opus 4.8 **提取偏多** |
| 最硬的一句 | 作者明确说：这些静态检查是"**风险证据，不是行为等价性的证明**"；两个策略都留下保持性风险，**不能当全自动重构工具用** |

**对我们的用法**：这是我们"三重门 + AST 白名单"的最强外部支持。别人做多 agent 精细流水线都做不到行为等价，**单一 gzip 口径更不可能**。

### 2.4 Shirafuji et al.：早一点的量化基线

arXiv **2311.11690**（APSEC 2023）：GPT-3.5 + few-shot 重构 Python，每题生成 10 个候选，**95.68%** 的程序能被重构，过滤掉语义不正确的之后平均 **圈复杂度 −17.35%、行数 −25.84%**。
顺带记录了一个坑：**会顺手删注释、翻译注释**（无关行为）。

## 五、族 3：程序精简 —— 被 agent 圈忽略、但方法论上最对味的一支 ★★★★★

这一族有 20 年积累，做的是：**给定一个"必须保持的性质"（通常是"还能复现这个 crash"），把程序缩到最小。**

**它和我们的问题结构完全同构**：

| 程序精简 | 我们的 harness 删减 |
|---|---|
| 输入程序 P | 当前 harness H |
| 性质 ψ(P)（crash 还在） | 行为等价（测试全过 + 分数不掉） |
| 每步产出一个更小的合法变体 | 每步删/并一处，产出候选 |
| oracle 判定 ψ 是否保持 | 三重门判定行为是否保持 |

### 3.1 方法演进（这条线值得在 related work 里单独起一段）

| 方法 | 出处 | 关键贡献 | 局限 |
|---|---|---|---|
| **ddmin** | Zeller & Hildebrandt 2002 | 把输入切成列表，删元素、看性质是否保持，二分收敛 | 不懂语法，大量候选语法非法，白跑 |
| **HDD** | Misherghi & Su, ICSE 2006 | 先转成语法树，按层做 ddmin | 仍只靠删除，不能做"提升/替换"这类变换 |
| **C-Reduce** | Regehr et al., PLDI 2012 | 一整套 C/C++ 专用变换，质量高 | **不通语言**，换语言要重写；慢 |
| **Perses** | Sun et al., **ICSE 2018** | **用文法约束每一步**，保证候选语法合法；支持删除之外的通用变换 | — |

**Perses 的实测**（直接可引）：结果大小是 DD 的 **2%**、HDD 的 **45%**；耗时是 DD 的 **23%**、HDD 的 **47%**；即便对比高度定制的 C-Reduce，也只用它 **38–60%** 的时间。

**为什么这一族对我们特别重要**：
1. 它给了"**语法引导的删减**"一个成熟框架——我们的 AST 级删减不是新发明，是这条线的自然延伸，**引用它比引用"MDL 类比"硬得多**
2. 它明确区分 **transformation space / search guidance / oracle engineering / validity control** 五个设计维度——我们的"四类算子 + 三重门"可以直接挂到这个坐标系上
3. 综述里已经出现"**LLM 提议重写 + reducer/oracle 兜底**"的新方向（`Program Reduction: A Comprehensive Survey`，Waterloo 预印本），说明"LLM 当提议者、传统 reducer 当验证者"这条路已经被认可

**但它有一个根本差异，必须写清**：程序精简的 oracle 是**一个二值性质**（crash 复现/不复现），便宜、确定。我们的 oracle 是**统计的**（通过率、带噪声）——所以 δ 和 k 次试验不可省。**这是我们把软件工程方法搬到 RSI 时必须补的一层，也是我们的技术贡献之一。**

### 3.2 HarnessMinimizer：名字撞车，但方法正好对得上 ★★★

| 项 | 内容 |
|---|---|
| arXiv | **2610.23054**（2026-10-16） |
| 注意 | 这里的 "harness" 是**库 fuzzing 的调用壳**，不是 agent harness。**别混用** |
| 做法 | 复用头部分析与预构建库/运行时加速每次构建；记录并重放输入值，删掉无关输入操作而不改变存活调用的值；用快速方法判断"简化后的 harness 是否仍复现原 crash" |
| 结果 | 200 个 crash、21 个库：比未优化流水线快 **3.46–4.51×**；harness 从平均 **1352 token 缩到 143–263 token** |
| 附带发现 | 用 LLM 做 crash 归因，**准确率从原始 harness 的 28% 提升到精简后的 44–51%** |

**最后这条对我们极有价值**：**精简本身提升了可诊断性**。这给了"K 下降不只是美观，而是让归因更容易"一个实证支点——正好呼应我们"简洁 harness 才可归因"的论证。

## 六、族 4：反方向 —— 把控制搬进代码，让上下文变短 ★★★★

### Growing Harness: Grow the Harness, Not the Context

| 项 | 内容 |
|---|---|
| arXiv | **2609.26760**（2026-09-22） |
| 作者 | Laizhen Li, Jiarui Li, Juanjuan Zhao, Kejiang Ye, Ye Li, Cheng-zhong Xu, Xitong Gao |
| 做法 | 从一个**无策略脚手架**（只有固定模型/工具接口，不含任何解题控制器）出发；失败时生成函数级执行 DAG，定位到具体函数，优化器**联合修复一批失败**；用**成功优先的 held-out 门**回滚伤害既有能力的修复序列 |
| 结果 | BrowseComp-Plus + WebArena-Verified，4B–120B 三个规模：六个设置里五个平均成功率最高；**LLM 调用 −76.0～91.8%，推理成本 −74.4～98.6%**；WebArena-Verified 上成功率在各规模稳定 **44.7–45.3%**，而 Tool-Calling 用 4B 模型掉到 **6.7%** |

**它和我们是"同源反向"**：
- 它：**代码变多，上下文变少** → 把重复的控制决策**编译进代码**
- 我们：**代码变短，能力不掉** → 把无收益的复杂度**削掉**

**必须回应的一句话**（审稿人一定会问）：
> "Growing Harness 证明了代码长是好事（把控制从上下文搬进代码能降 98% 成本），你压代码不是反着来吗？"

**答法**：区分"**承载控制的代码**"和"**不承载控制的代码**"。前者该长（它是被摊销的确定性逻辑），后者该删（它是没被测过的冗余）。K 惩罚必须带**防御白名单 + 行为等价门**，正是为了不误伤前者。这不是口号——我们的对照组就该是"删掉的那部分到底是不是控制代码"。

## 七、族 5：技能与工作流抽象 —— "压缩"的另一种形态

| 工作 | 编号 | 做什么 | 对我们的意义 |
|---|---|---|---|
| **Voyager** | 2305.16291（NeurIPS 2023） | 技能库：验证过的可执行代码存成向量索引的子程序，可组合、可零样本复用 | "代码即技能"的源头。它证明了**抽象复用**能积累能力 |
| **Agent Workflow Memory** | 2409.07429 | 从轨迹里抽子任务套路，**剥掉例子专属的具体值**，层级化复合并入 | "剥掉具体值"就是**抽象化压缩**的最小动作 |
| **Externalization in LLM Agents**（综述） | 2604.08224 | 把记忆/技能/协议/harness 工程统一成"外化"框架；技能获取分 撰写 → 蒸馏 → 发现 → 组合 四条路 | 综述级引用，用来交代"harness 是什么"很省事 |
| **Lost in Implicit Routing** | 2610.18522 | 固定任务与金标准技能，只加无关技能做干扰：1000 个干扰项时，加载召回从 **73.6% → 27.4%**，零加载率 9.3% → 51.6%；而显式预选同库仍保持 **73.9%** | **技能库膨胀的代价是"加载失效"**。这是"K 膨胀"的第二种危害——不只是贵，是**用不上** |

> 最后这条是 C 级（来自研究日报），引用前必须打开 arXiv 核。

**这一族对论文的意义**：它提供"压缩"的**第二种收益口径**——不只省 token，还**提升可检索/可组合性**。如果我们能把"K 降低 → 技能可被正确加载"做成一条观察，那就不只是"省"，而是"变得可用"。这是个还没人做的角度。

## 十、我们还能站的位置（按硬度）

**空位 1：K 作为回路内的接受准则，且可单独否决 ★★★★★**
仍然成立。所有对手里，最接近的 SHarP 用的是 token 成本、且是事后剪枝；HarnessDev 只把 LOC 当**描述变量观察**，还得出"行数不预测性能"的负结论。**"K 能独立否决一个候选"这件事，没有先例。**

**空位 2：统计 oracle 下的程序精简 ★★★★**
程序精简那条线（Perses 等）oracle 是二值的、便宜的。搬到 harness 上，oracle 变成**带噪声的通过率**——于是必须补 δ、补 k 次试验、补"删完真去跑"。**这一步在软件工程侧没人做，在 RSI 侧也没人做**（RRSI 的 pruner 是启发式，删完不跑）。

**空位 3：把"压缩的收益"从成本改成可诊断性 ★★★**
HarnessMinimizer 给了一个支点：精简后 LLM 归因准确率 28% → 44–51%。ACON 给了反面：历史压缩不省钱（KV-cache 抵消）。**两条合起来说明：卖"省钱"会挨打，卖"可归因 / 可审计"站得住。** 这个角度目前没人占。
