# 反思：从「实验平台」到「自改进 agent」

2026-11-01 ｜ 触发：用户指出"最终交付的是一个自改进 agent，简化代码只是它的众多功能之一"。
方法：**十遍，每遍换一个角度，只保留能改变架构的结论**。凡没改变架构的，记在末尾"想过的但没用的"。

---

## 第 1 遍 · 主客体是不是颠倒了

**我原本的设定**：`exp` 是外壳，`adapt/` 里装的是别人的 agent（Terminus-2 / mini-swe-agent），
工具做的是"包住它们、测它们、拆它们"。

**推演**：在这个设定里，"被测对象"是主体，"工具"是观察者。
可用户说的是"**交付一个自改进 agent**"——主体是那个 agent，工具是它的**身体**。

**证据（自证）**：如果主体是 agent，那"它如何决定下一步改什么"必须有一个模块。
我的 `16` 里没有这个模块——`runner` 只会"跑一次评测"，`counterfactual` 只会"删一轮组件"。
**一个不会决定自己下一步做什么的东西，不叫 agent。**

**结论：主客体颠倒。** 平台是它的**运行设施**，不是它的身份。
上一轮我把"可复现"当第一优先（run_id / cmd_hash / manifest 做得很重），
而"它能不能自己转起来"反而没有模块——这就是颠倒的直接后果。

---

## 第 2 遍 · "众多功能之一"这句话，我的架构接不住

**我原本的设定**：删除是唯一功能，`counterfactual.py` 是核心，其他都没有。

**推演**：一个有"众多功能"的主体，必须有一个**统一的算子接口**——每个功能都是一个算子，
实现同一个 `propose(state) -> list[Candidate]`。没有这个接口，"之一"就无从谈起。

**证据**：我的 `remove/` 目录是硬编码的一条路（static → mutate → counterfactual），
它不是"一个算子"，它是"整个流程"。所以架构上**加了第二个功能无处安放**。

**结论**：必须引入 `Op` 协议 + 算子注册表。删代码只是注册表里的一个条目。
这条不是"锦上添花"——**没有它，"简化是众多功能之一"这句话在代码里不成立。**

---

## 第 3 遍 · "自"字是空的

**我原本的设定**：`adapt/harness_code.py` 的 `apply()` **直接抛 `PermissionError`**，
理由是"所有改写必须指向 worktree 副本，不能碰原库"。

**推演**："自改进"的技术含义是：**主体改的是它自己**。
如果工具永远只能改"别人仓库的副本"，那它是"改进器"，不是"自改进 agent"。

**证据**：`src/adapters/harness_code.py:135-139` 那段 PermissionError 的注释写得很清楚：
"所有改写必须指向 worktree 副本"。这条规则在"M0 实验"语境下是对的（保护上游仓库），
但在"自改进 agent"语境下是**致命的**——它从代码层面禁止了"改自己"。

**结论**：agent 必须有**自己的身体目录** `body/`：
- 初始化时从上游 fork 一份（git worktree 或 copy）
- 算子改的是 `body/` 里的文件
- 采纳后 `body/` 前进，旧状态进 archive
- **它改的是自己，不是别人的仓库**

---

## 第 4 遍 · 创新点被我摊薄了

**我原本的设定**：K 度量在 `measure/`，删除在 `remove/`，判定在 `judge/`——三个平行模块，三层各管一段。

**推演**：论文的创新点不是"我们有 K"，也不是"我们会删"，而是
**"删除这件事自带因果证据"**——删掉 → 真跑 → 分数不掉 → 这条证据链闭合。

证据链一旦被拆到三层，它就不再是"一个功能的证据"，而是"三个模块的产物"。
更糟：如果这三个模块还被别的功能复用（K 被 rewrite 用、judge 被所有算子用），
那"删除的因果证据"在代码里就**找不到一个完整的落点**。

**结论**：`ops/simplify/` 必须是**内聚的一个包**：
度量 K → 客观切分 → 找可删 → 物化删 → 真跑 → 三态/四态 → 出证据表。
对外只暴露两件事：`propose()` 和 `evidence()`。
**创新点的位置 = 一个目录，不是三层。**

---

## 第 5 遍 · 那"其他功能"具体是什么（不能空谈）

必须具体化，否则"众多功能之一"是口号。

| 算子 | 做什么 | ΔK 方向 | 自带因果证据？ | 别人做过？ |
|---|---|---|---|---|
| **`simplify`** | 删组件 | **↓** | **✅ 反事实删测** | RRSI 的 pruner 只报不删 |
| `rewrite` | 改 prompt 措辞/结构 | ~ 或 ↑ | ❌ 只有分数涨跌 | RRSI 主路 |
| `tune` | 调参数（步数上限、上下文阈值、压缩比） | ~ | ⚠️ 可做 A/B | HarnessPro |
| `augment` | 加 middleware / 加工具 | **↑** | ❌ | AHE（增益主要来源） |
| `route` | 换底座 / 模型档位 | — | ❌ | 常见工程手段 |

**关键观察**：五个算子里，**只有 `simplify` 的 K 方向是确定的（必降）**，
其余四个的 K 方向都不确定甚至上升。这解释了为什么 K 必须能**否决**——
它是给那四个算子上的闸门。**删测自己不需要这道闸门。**

**结论**：架构上留 5 个算子位；实现上 v1 只做 `simplify`，其余标 stub（接口在、实现空、不参与验收）。
这不是半成品，这是**明确的边界**：`14` 的非目标写着"不自研 agent 框架"，
把 5 个算子都做完等于自研一套演化框架。

---

## 第 6 遍 · 判定器的正确位置（上一轮批判的续）

**上一轮我说**：判定器在纯删除流程里恒为真，K 否决永不触发，是死代码。

**现在看**：这个批判成立，但**结论错了**。正确的结论不是"删掉 K 否决"，
而是"K 否决的消费者不是删测，是其他算子"。

- `rewrite` 把一段 prompt 从 3 行改成 8 行 → K 涨 → **必须拒**（除非分数显著涨）
- `augment` 加一个 middleware → K 涨 → **必须拒**（这是"常驻臃肿"）
- `simplify` 删一个组件 → K 降 → 闸门自动放行，但**它要过自己的证据关**

**结论**：两层判定，父子关系：

```
simplify 的候选 → ① 算子的证据关（删测可信？三态/四态）→ ② 全局闸门（K 降 + S 不掉）
其他算子的候选 → 直接进 ② 全局闸门
```

①是 `ops/simplify/evidence.py`，②是 `gate.py`。**两层职责不同，不是重复。**

---

## 第 7 遍 · 记忆在哪

**推演**：自改进 agent 一定会重复试错——除非它记得"上次删这个组件掉分了"。

RRSI 用 git worktree（每候选一个 commit），DGM 用 archive，SICA 用 self-feedback 日志。
三者共有一个东西：**候选档案**。

**证据**：我的架构里只有 `record.py`（一次 rollout）和（上一轮才补的）`incumbent`。
**没有"试过什么、结果如何、为什么被拒"**——agent 会无限重试同一个失败候选。

**结论**：`archive.py` 三张表：
- `candidates`：候选 id / 算子 / diff / 判定 / 证据路径（= 十类字段第 9 类的载体）
- `incumbent`：当前最佳（一个 commit 指针 + 它的 S/C/K）
- `rejected`：被拒候选的**指纹**（防重复提案）

这不是"日志"，是 agent 的**记忆**——没有它，"自改进"退化成"随机搜索"。

---

## 第 8 遍 · 课题名里的"用户反馈闭环"去哪了

**推演**：课题名是"面向用户反馈闭环"。我的架构里反馈只有一种：benchmark 的 S。
`00_总纲` 自己也承认"反馈源为代理指标（task_completion）"。

**但如果是自改进 agent，反馈是它的输入源之一**：
- 内部反馈：benchmark 判分（确定性）
- 外部反馈：真实使用中的失败样本

**证据**：`src/domain/sample_pool.py`（失败样本池，版本冻结）我上一轮判定为"另一件事，不动"。
**这是错的**——它是外部反馈进系统的那道门。

**结论**：`feedback/` 至少要有接口：把一条真实失败转成 `Task` 并投进 `evolve` 池。
v1 可以只做"从 jsonl 读"，但**接口必须在**，否则"反馈闭环"四个字在代码里没有落点。

---

## 第 9 遍 · 自主性与可复现的张力（必须承认的代价）

**推演**：agent 自己决定下一步改什么 → 它的轨迹是**它选的**，不是预设的实验矩阵。
那么"论文里每个数字都能追到一条命令"这句话，就变弱了。

- v1（平台）的可复现单位 = **一条命令**（`run --agent X --seeds 3`）
- v2（agent）的可复现单位 = **一条轨迹**（trajectory：每步的 state hash + 决策 + 证据）

**结论**：不要假装两者一样。如实分开：

| 类型 | 复现方式 | 强度 |
|---|---|---|
| 评测（给定 harness 跑基准） | 命令 + commit + seed + 配置哈希 | **强**（字节级） |
| 演化（agent 自己选路） | 轨迹重放（state hash 链）+ 同种子 | **中**（同种子下决策序列可重演，但外部服务非确定） |

论文里必须写清：主结果表的每一格是**强复现**（评测），
演化轨迹是**中复现**（重放）。混着写会被抓。

---

## 第 10 遍 · 如果我错了呢（反驳自己）

**假设**：用户其实还是要"实验平台"，只是措辞不同。

**判断依据**：
1. 用户原话是"交付的是一个**自改进 agent**"——不是"一个自改进**工具**"或"平台"。
2. "它也要有简化代码的功能"——"功能"是 agent 的词汇（平台有"能力"、"模块"，没有"功能"）。
3. "这个简化代码只是它的**众多功能之一**"——明确说主体有多个功能。
4. 课题名"研发实验自动化与**自迭代**"——自迭代的主语是系统本身。

**结论**：判断成立，v1 的方向反了。但 v1 不是白做：
它把"评测、记录、判定、报表"这套**设施**设计清楚了，而这套设施在 v2 里原封不动地变成 agent 的**观测层**。
**改了的是身份，不是零件。**

## 想过的但没改变架构的

- 要不要把 `reuse.py` 的单点引用改成子包：想过，不改，理由不变（防两份实现分叉）。
- 要不要用 typer 替代 argparse：不改。`14` 的非目标是"别重造"，argparse 够用。
- 要不要做 Web 看板：不改，非目标写死了。
- 算子要不要支持 LLM 生成候选（RRSI 的 proposal network）：v1 不做。
  理由：`simplify` 的候选**不需要 LLM**——删什么由静态分析 + 覆盖决定，这是它的优点（便宜、可复算）。
  一旦引入 LLM 提案，就把"可复算"换成"看模型心情"。

## 结论：v2 的定位

> **交付物是一个自改进 agent。它以自己为改造对象，有多个改进算子；
> 其中 `simplify`（删代码）是唯一自带因果证据的算子，也是论文的创新点。
> 平台属性（记录、判定、报表）是它的观测设施，不是它的身份。**

### v1 → v2 的七处改动

| # | v1（平台版） | v2（agent 版） | 改了为什么 |
|---|---|---|---|
| 1 | `exp` 是外壳，agent 是被测对象 | **`self` 是主体**，`body/` 是自己的 harness | 主客体颠倒 |
| 2 | 删除是唯一流程 | **`ops/` 算子注册表**，`simplify` 是其一 | "众多功能之一"要落地 |
| 3 | 适配器只读，改写抛 PermissionError | **算子改 `body/`**，采纳后前进 | "自"字 |
| 4 | K/删测/判定散在三层 | **`ops/simplify/` 内聚**，对外只出 `propose` + `evidence` | 创新点要有一个目录 |
| 5 | `gate` 是唯一的判定 | **两层**：算子证据关 + 全局闸门 | K 否决的消费者是其他算子 |
| 6 | 无演化循环 | **`agent.py` 主循环** + `archive.py` 记忆 | 不会决定下一步的不叫 agent |
| 7 | 反馈只有 benchmark | **`feedback/`** 接口（外部失败 → evolve 池） | 课题名有"用户反馈闭环" |

**不变的三条**（上一轮说"坚持"的，这一轮仍然坚持）：
K 离线算 · 删除必须物化 · 另起包不改造 `src`。
