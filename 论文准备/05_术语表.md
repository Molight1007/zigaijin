# 05 术语表

> **一句话**：先记住三组最容易混的词，其余按需查表。

| 容易混 | 区别一句话 |
|---|---|
| **TB2 vs Terminus-2** | TB2 是**卷子**（89 道题），Terminus-2 是**考生**（agent） |
| **S vs C vs K** | S 是分数、C 是跑一次花多少、K 是**交付物本身有多长** |
| **"没测出影响" vs "没用"** | 前者是样本量不够，后者是结论；**不能说反** |

## 一、系统与对象

| 术语 | 定义 | 具体所指 / 本项目用法 |
|---|---|---|
| **Harness（外壳）** | 模型权重之外、决定"怎么用模型"的全部可编辑组件 | 提示词、控制流、工具定义与实现、middleware/hook、记忆、子 agent、技能文档。**不是模型本身** |
| **H0 / 初始 harness** | 演化开始前的那个 harness，一切增益的对照基准 | RRSI 编码域 H0 = Terminus-2；AHE 的 H0 = 一个只有 shell 工具的弱种子 |
| **Backbone / Policy model（底座）** | 被 harness 包住的、权重冻结的模型 | 本文档常写成"底座"。ModularRSI 与 TTHE 都用 **DeepSeek-V4-Flash** |
| **Terminus-2** | Terminal-Bench 官方提供的一个 agent 实现 | **是被测 agent，不是模型也不是测试集**。RRSI、ModularRSI 拿它当 H0 |
| **Codex CLI / Claude Code** | OpenAI / Anthropic 官方的命令行 agent | HarnessPro、RHO 拿它当 H0；Meta-Harness、RRSI 拿它当"提案者" |
| **Harbor** | Terminal-Bench 的评测运行框架 | 负责起容器、跑题、判分。ModularRSI 用它，我们也要用 |
| **Adapter（适配层）** | 把"我们的流程"接到"别人的 agent/数据集"上的薄层 | 计划书里"只写三样"之一：接不同 agent 的适配层。**这是我们的必需件** |
| **Domain adapter** | 一个 **领域 = 一个适配器 + 一个起始 harness** | RRSI 的三域（编码/法律/工程）就是这么组织的，接口形状值得抄 |

## 二、演化与流程

| 术语 | 定义 | 具体所指 / 本项目用法 |
|---|---|---|
| **RSI（递归自我改进）** | 用系统自己的产出反馈，反过来改进系统本身 | 这里特指"改进 harness"，不训练权重 |
| **Proposer（提案者）** | 读历史与失败，提出下一版 harness 的组件 | 常见做法是给 coding agent 一堆轨迹让它诊断 |
| **Critic（审查者）** | 在**评测之前**筛掉"只对这道题有效"的提案 | RRSI 的关键设计：**先拦再评**，不能让泄漏的候选先拿到虚高分 |
| **Pruner（剪枝器）** | 删掉"太小 / 太贵 / 已无用"的组件 | 注意：RRSI 的 pruner 只是把组件**报给提案者当删除目标**，并没有"删了真跑" |
| **Selector（选择器）** | 在候选里决定谁成为下一代 incumbent | RRSI 用"地板 + 成本条件 + 分数最高"三条 |
| **Incumbent（在位者）** | 当前被采纳、正在被评测的那一版 harness | RRSI 用 git 分支管理，incumbent 永远是一个 commit |
| **Round / Epoch（轮 / 代）** | 一次"提案 → 评测 → 采纳"的完整循环 | RRSI：T=20 轮；ModularRSI：5 模块×3 + 整合 1 = **16 epoch** |
| **Rollout（采样轨迹）** | 让 agent 在某道题上完整跑一次 | ModularRSI 每任务 n=3 条轨迹 |
| **Ablation（消融）** | 去掉某个组件/机制，看指标掉不掉 | 我们要做四组：K 否决、白名单、单池、启发式删 |

## 三、评测与数据

| 术语 | 定义 | 具体所指 / 本项目用法 |
|---|---|---|
| **Benchmark（基准）** | 一套标准化题目 + 判分器 | TB2、SWE-bench Verified 等 |
| **Terminal-Bench 2（TB2）** | **测试集**：89 道容器化终端任务 | **2.0 与 2.1 是不同版本，分数不可混用**。我们两版都跑 |
| **SWE-bench Verified** | **测试集**：500 道人工验证过的真实仓库修 bug 题 | 跨分布评测的主力 |
| **SWE-Bench Pro** | 更长程、更难的软件工程集 | HarnessPro / RHO / HarnessDev 用 |
| **Evolve set（演化集）** | 演化过程中**看着它调参**的那批题 | 相当于训练集 |
| **ID held-out（同分布留出）** | 同基准里没参与演化的一部分题 | RRSI 的 Harvey LAB 160 = 120 演化 + 40 留出 |
| **OOD（分布外）** | 换一个不同基准来测，检验是否只对原题有效 | 防"基准专用拟合"的关键测量 |
| **演化池 / 量外池** | 我们的双池设计：日常迭代用演化池；量外池在迭代期**封存**，只用于最后测过拟合 | 对应 RRSI 的 evolve / held-out，但我们要把**两池分数差本身**报成一个指标 |
| **Coreset（核心集）** | 从大批题里挑出的代表性小批 | HarnessPro / RHO 用 DPP 挑 k=10，且全程固定 |

## 四、统计

| 术语 | 定义 | 具体所指 / 本项目用法 |
|---|---|---|
| **δ（噪声带 / 地板）** | 同一个 harness 重复评测时的自然波动范围 | **必须实测，不能拍**。RRSI 实测：TB2.1 上 3 个 pass、Harvey 上 60 条判据 |
| **S\*（地板基准）** | 接受新候选的分数下限，通常写成 `S ≥ S* − δ` | 注意 S\* 是**固定的历史最好**，不是"上一轮"——否则 T 轮会累积掉 T·δ |
| **Bootstrap（自助重采样）** | 反复从已有样本里有放回抽样，估计指标的分布 | RRSI 与 ModularRSI 都做 **任务级配对** bootstrap，10,000 / 100,000 次，取 2.5/97.5 分位为 95% CI |
| **Paired（配对）** | 两个方法在同一批题上比，而不是比总体均值 | 配对能消掉题目难度带来的方差，是正确做法 |
| **CI（置信区间）** | 指标的不确定范围 | 报数必须带，否则"涨了 2 分"可能只是噪声 |
| **Pass@k / Pass^k** | 前者= k 次里至少成功一次；后者= k 次全成功 | ModularRSI 两个都报（Pass@3 / Pass³），口径不同不可混 |

## 五、目标与指标（这一组是我们论文的核心）

| 术语 | 定义 | 具体所指 / 本项目用法 |
|---|---|---|
| **S（能力）** | 通过率类指标 | 主目标 |
| **C（成本）** | 执行成本，通常用 policy token 或美元 | RRSI 的"complexity-aware acceptance"实际管的就是它 |
| **K（描述长度）** | **harness 源码/文本有多长**，用可复算的标量表示 | **我们的第三目标**。注意 RRSI 也叫"complexity"，但它用 token 成本代理，且自称"类比" |
| **ΔK / ΔS / ΔC** | 候选相对 incumbent 的变化量 | 判定用：ΔS 超过 δ 之后，再看 ΔK 与 ΔC 是否付得起 |
| **Pareto dominance（帕累托支配）** | A 在所有维不差、且至少一维更好 → B 被淘汰 | 三方帕累托：S 不低、C 不高、K 不高 |
| **Veto（否决项）** | 某一维不满足就直接淘汰，不能被其他维补回来 | 我们要让 **K 能单独否决**，而不是只进加权分 |
| **MDL（最小描述长度）** | 用"能压缩数据的最短描述"来选模型 | K 的理论根：压缩即理解。Rissanen 1978；Kolmogorov 复杂度是它的不可计算理想版 |

### K 的候选口径（**必须先冻结，定了就不能改**）

| 代号 | 口径 | 优点 | 缺点 |
|---|---|---|---|
| K1 | UTF-8 字节数 | 零歧义、任何人可复算 | 对中文/英文不敏感 |
| K2 | 非空行数 | 最直观，人肉可数 | 一行写 500 字也算 1 |
| **K3（建议主口径）** | **去注释后的 token 数**（公开 tokenizer + 版本号） | 对"堆废话"最敏感，跨文件类型可比 | 依赖 tokenizer 版本 |
| K4 | AST 节点数（仅代码） | 能识别"结构变复杂了" | 只适用于代码，不适用提示词 |

**建议**：主报 **K3**，同时**永远附报 K1 与 K2**（便于他人复算与质疑），代码侧另报 **K4** 用于防御白名单判定。
所有 K 都按组件分组报：`system prompt / tools / middleware / memory / subagent / skills`。

## 六、过拟合与防线

| 术语 | 定义 | 具体所指 / 本项目用法 |
|---|---|---|
| **基准专用拟合（benchmark-specific fitting）** | harness 把题面特征、答案、领域词写死，看起来涨分其实只是背题 | RRSI 的三条过拟合来路之一，靠 critic 在评测前拦 |
| **噪声追逐（noise chasing）** | 把随机波动当成真实提升 | 靠 δ 地板拦 |
| **复杂度累积（complexity accumulation）** | 不断加东西，演化集涨分但底层机制没变好 | **我们的 K 正是打这个**。RRSI 只定性讨论，没量化 |
| **泄漏（leakage）** | 把评测集信息带进了交付的 harness | 判据是"交付的 diff 里有没有题面/答案"，不是"提案理由里提没提" |
| **死组件（dead component）** | 写了但从来没被执行到 | HarnessDev 实测：108 个组件只有 72 个被执行过 |
| **防御式代码（defensive code）** | 参数校验、断言、异常兜底、边界处理 | **压缩时必须白名单豁免**，否则 K 会systematically 逼着删掉它们，系统变脆 |
| **反事实删测** | 把某一段单独删掉、**真跑一遍**，看分数掉不掉 | 我们的核心证据形式。对手的 pruner 只"判断"，我们"实测" |
| **行为等价回归** | 删完之后"能力不变"要有测试背书 | 老师报告四阶段路线的每层都要求做 |

## 七、一句话索引（记不住时看这里）

- **卷子** = benchmark（TB2 / SWE-V）
- **考生** = harness（Terminus-2 是其中一种现成的）
- **大脑** = backbone（DeepSeek-V4-Flash）
- **考试流程** = evolve → 评测 → 采纳，一轮叫 round/epoch
- **防作弊** = critic（评测前拦）+ δ 地板（拦噪声）+ 双池（拦过拟合）
- **我们的卖点** = 在 S 不降的前提下把 **K** 压下来，且这个"压"有**删测证据**
