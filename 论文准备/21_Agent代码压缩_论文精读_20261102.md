# 族 0：直接把模块拔掉

这两篇是**和我们在同一层动手**的工作。先说它们，因为审稿人一定会拿它们问你。

## 1. SHarP：把 harness 当神经网络剪枝 ★★★★★

**【精读】** `2610.04178` · UCSB + MIT-IBM Watson AI Lab + Adobe Research · 2026-10-03 · 代码 `github.com/UCSB-NLP-Chang/SHarP`

### 一句话

> 把 agent 的工具、指令、机制当成"可以一个个拔掉的插头"，逐个拔一遍看掉不掉分、省不省 token，然后把"既不影响干活又费电"的拔掉。结论是：**大部分 harness 里有一大半是白装的。**

### 它治什么病

想象一台电脑，每次卡顿就装一个插件，装了三年。现在没人知道哪个插件有用——因为**从来没人敢拔**（怕拔了出事）。

harness 就是这样长起来的：agent 每次失败，开发者就加一条指令、加一个工具、加一道检查。**只加不减，而且没人测过每条到底有用没用。**

作者原话很狠：harness "tend to grow monotonically in size and complexity"（单调地越长越大）。

### 怎么做（四步）

| 步 | 动作 | 关键细节 |
|---|---|---|
| 1 | **切模块** | 按实现边界切：一个注册的工具 = 一个模块；一个带标题的指令块 = 一个模块；一个独立处理机制 = 一个模块。**强耦合的要合并**（工具 + 它的使用说明算一个） |
| 2 | **算显著性** | 对每个模块，**只关掉它、其他全开**，在同一批开发任务上跑一遍。记两件事：分数变了吗、token 变了吗 |
| 3 | **两种剪法** | **效率优先**：先保护"拔了会掉分"的（配对 t 检验 p≤0.05），剩下的按"拔了省 token 最多"排序，从省得最多的开始拔。<br>**性能优先**：反过来 |
| 4 | **在验证集上验收** | 每档剪法都跑 3 次取平均，画"性能 × token"的帕累托前沿 |

**为什么这个设计聪明**：它只需要 `1 + m` 次评测（全量 1 次 + 每个模块各 1 次），不是 2^m 次组合。这是它敢做 27 个模块的原因。

### 数字（原文表与图）

5 个设置 / 4 个 harness / 底座统一 Qwen3.5-122B-A10B：

| 设置 | 全量 harness | 剪完最好的一档 | 变化 |
|---|---|---|---|
| **OpenHands / GAIA**（27 个模块） | 29.44% | 剪掉 24 个 → **35.00%** | 分数 +5.56pp，token 也降 |
| OpenHands / GAIA（全拔） | — | 剪掉 27 个 → 14.44% | **拔过头会崩** |
| **JIT agentfold / DeepPlanning**（性能优先） | 75.8% | S'19 → **82.5%** | 分数 +6.7pp，token −5.9% |
| JIT agentfold（效率优先） | — | S20 → 76.2% | 分数持平，token **−39.0%** |
| LIFE-harness / retail（效率优先） | — | S43 → **87.5%** | 最高分档 |
| LIFE-harness / retail（性能优先） | — | S'7 → 70.0% | token **−21.2%** |
| PaperQA2 / LitQA2（18 个模块） | 全量最好 | 剪了都掉分 | **这个 harness 不冗余** |

**最扎心的一句话**：OpenHands 和 LIFE-retail 上，**全量 harness 落在了帕累托前沿之外**——意味着"少装点"严格优于"全都装"。

### 软肋（这几条就是我们的空位）

| 它的问题 | 具体 |
|---|---|
| **判据是 token，不是代码长度** | 全文没出现 description length / LOC / Kolmogorov / MDL。它的"效率显著性"是**运行时 token**。一个模块可以零 token（比如永远不会被调用的工具描述在别处）却占 200 行代码 |
| **是事后剪一刀，不在回路里** | 训练完 → 剪一次 → 完。它拦不住"越改越胖"这个过程本身，只能事后瘦身 |
| **粒度是整块开关** | 不能做"改代码但行为不变"，只能"这个模块开或关" |
| **只谈性能 × token，不谈泛化** | 没有 OOD、没有过拟合度。它的验证集是 held-out，但不是"演化期禁用"的量外池 |

### 我们能拿来干什么

1. **当最强的动机引用**：「harness 高度冗余，剪完性能不掉甚至涨」这件事它已经用 5 个设置坐实了。我们不用再论证前提，直接接"**那怎么判该剪谁**"。
2. **当 baseline**：它的效率优先档就是"token 口径的剪枝"。我们要证明的是"同分数下 K 更低"能剪出**它剪不动的东西**（因为它不看见代码长度）。
3. **抄它的评测经济学**：`1 + m` 次单模块消融。我们的四类算子如果按"每个算子一次全量消融"来测，成本可控。

## 2. Cortex：每加一句提醒，都要先做对照实验 ★★★★

**【精读】** `2610.14216` · 独立研究者 Samuele Giampieri · 2026-10-09 · 46 页（含大量图表与协议）

### 一句话

> 给 agent 写"注意事项"（CLAUDE.md / skills / rules）时，**别凭感觉加**。每加一条，就"带这条 / 不带这条"各跑好几遍，真有用才留；删也一样。而且**只统计"agent 真的看到过这条"的场合**。

### 它治什么病

文档是怎么长出来的：同一个错犯两次 → 记一行 → 这行永远留着 → **每轮每一步都在为它付上下文费**。

而"这条到底有没有用"的判断方式，往往和写它的方式一样草率——**某人看它生效过一次，就算数了**。

作者给了一个必须记住的数字：

> 同一个 harness、同一批任务、分两批 rollout 重测，**差 −3.3 个百分点，95% CI [−7.3, 0.0]**。
> **"这个差异只看一次，会被当成真效应。"**

这就是"δ 必须测出来"的又一份实证。

### 怎么做（三个命令 + 五道门）

**三个命令**：
- `/harvest`：一次调试会话结束（从坏到好），把这个修复存成**可回放的任务**
- `/evolve`：跨会话找**反复出现**的纠正 → 一次只写**一条** skill 或 rule → 做对照实验
- `/prune`：对已经在里面的每条，**删掉它再跑一遍**，证明确实没用才删

**五道接受门（原文表 3，τ=0.34，m=2 次）**：

| 门 | 条件 | 为什么 |
|---|---|---|
| 0 | 可评分，且（若被加载过）有提升空间 | 数据坏了、或本来就没得涨，不算证据 |
| 1 | **G > 0** | 必须赢点什么 |
| 2 | **D ≤ τ** | 不许有任何一道题崩掉 |
| 3 | **对所有"从没失败过"的题，候选必须全过** | **没失败过的题不给容差** |
| 4 | **k·N ≥ m** | 一次赢是抛硬币 |
| 5 | **f ≥ 1** | **从没被触发过的候选，不能算有功** |

**门 3 和门 5 是这篇最值钱的两个设计**：
- 门 3 堵死了"在本来就会做的题上刷分"
- 门 5 堵死了"加了但模型没读到，却算它有用"

### 还有一件被大多数人忽略的事：曝光

它只给**被加载过的任务**打分。原文例子：一条 rule 在 26 道题里只有 6 道真的进了上下文，**就只算这 6 道**——其余 20 道两道臂只差噪声，算进去就是稀释信号。

### 数字

| 项 | 值 |
|---|---|
| 主结果 | evolved 76.5% vs 无 skills/rules，**+55.0pp**，95% CI [+34.1, +74.1]，置换检验 p=0.0001 |
| 归因 | **rules（自动加载）干了大部分活**；skills（模型自选打开）只在"跟着任务涉及的文件一起给"时有用；每轮都摆在面前的 skills **很少被打开** |
| 强模型 | Claude Sonnet 5 上单轮 harness 增益很小 |
| 真项目 | 真实开源项目上"没找到可学的东西"（因为很少被纠正） |
| 植入的有害规则 | **没能识别**。作者自己写清：*"这证明 Cortex 不留没用的文本，不证明它能识别有害文本"* |

### 软肋

- 单作者、单模型（Haiku 4.5 为主）、**自建仓库不是公开 benchmark**
- 46 页里很大篇幅是协议与图示，实验规模小
- **证据强度按 B 看**，不能当定论引用

### 我们能拿来干什么

1. **门 3 / 门 5 直接可搬**：我们的"删除覆盖率"口径里，"没声明算 unverifiable"和它的门 5 是同一个思路。
2. **曝光过滤进我们的评测协议**：如果一段 harness 文本在某个任务上根本没进上下文，这个任务的分数差**不该计入**。这条我们现在没做。
3. **δ 的引证**：−3.3pp / CI[−7.3, 0] 是"重复测量散布有多大"的现成证据。

# 族 1：先把"烂"量出来

## 3. SlopCodeBench：agent 写的代码，越改越烂 ★★★★★

**【精读】** `2603.24755` · UW-Madison + WSU + MIT · 2026-03 · 代码 `github.com/SprocketLab/slop-code-bench`

### 一句话

> 让 15 个 agent 接手**自己上一版的代码**、连续改 3–8 次需求，然后量化两件事：**代码变啰嗦了多少**、**复杂度往少数函数里挤了多少**。结论：**没有 agent 端到端做对任何一题**，而且质量**每轮都在掉**。

### 它治什么病

现有 agent benchmark 都是**单发**的：给完整规格，一次写完，跑测试，打分。

但真实开发是**迭代**的。单发 benchmark 有个致命盲点：**代码可以过测试，同时越来越难改**。

而且以前的迭代 benchmark 有个问题——它们从人类仓库的 commit 历史出题，**agent 从来不用为自己早期的设计决策付代价**。这篇的不同：**从零开始，自己选架构，然后自己承担后果。**

### 两个度量（这两个定义值得抄）

**① 结构侵蚀（erosion）**——复杂度是否挤在少数函数里

```
每个函数的"复杂度质量" = CC × √(SLOC)
erosion = 质量落在 CC>10 的函数上的比例
```
（CC = 圈复杂度，阈值 10 跟 Radon 工具的惯例）

**为什么用 √SLOC**：让"复杂度"主导而不是"行数"。作者举例：一个 `find_matches_in_file()` 长到 117 行，每种规则、每种匹配来源都在同一个循环里串起来。

**② 啰嗦度（verbosity）**——冗余代码占比

```
verbosity = |被标记的行 ∪ 克隆行| / LOC
```
被标记的行来自 **137 条 AST-Grep 规则**（观察到的啰嗦写法 + 最佳实践 + 社区常提的反模式）；克隆行用 clone detection。**多规则命中同一行只算一次。**

**它顺便否掉了几个常见替代品**：可维护性指数（太综合，看不出具体怎么变坏）、单独的 CC（看不出集中）、单独 LOC（看不出重复）。理由是：**"更啰嗦"和"更侵蚀"是两种独立的坏法，得分开量。**

### 数字

| 项 | 值 |
|---|---|
| 规模 | 36 题 / **196 个检查点** / 15 个 agent（6 家） |
| 通过率 | **没有 agent 完整解出任何一题**；最高严格通过率 **14.8%**（GPT-5.5）；最好核心通过率 67.3%（Opus 4.5） |
| 越改越差 | **erosion 在 77% 的轨迹里上升，verbosity 在 75.5% 里上升** |
| 相对人类 | 对比 **473 个开源 Python 仓库**：agent 代码 **侵蚀 2.0×、啰嗦 2.3×** |
| 越改越贵 | 每个检查点的成本持续上升，**但正确率没跟着涨** |
| 提示有没有用 | **质量提示能把初始 erosion 降 62.3%、verbosity 降 34.8%，但恶化速率不变**（平均每检查点仍掉 1.3pp），而且**每检查点成本还涨 12.1%** |
| 核心通过率趋势 | 从 64.6% 掉到 35.5%，core 与 iso 的差距从 2.5× 拉到 5.4× |

### 软肋

- **版本会变**：v1 是 20 题 / 93 检查点 / 2.2× / 80% 与 89.8%；现版是 36/196 / 2.3× / 77% 与 75.5%。**引用必须锁版本。**
- 它只测**测不压**：给了病，没给药
- erosion/verbosity 都是**比例**，不是绝对量

### 我们能拿来干什么

**这是我们最强的"病"的引证。** 三句话可以直接用：
1. "agent 代码比人啰嗦 2.3 倍"——跨 15 个 agent、473 个仓库
2. "提示它写干净点没用，只降初始值，不改恶化速率"——证明**必须有选择压力，不能靠嘱咐**
3. "复杂度在 77% 的轨迹里单调上升"——证明这是**结构性**问题

**但要小心一个反噬**：`verbosity` 已经在被当指标测了。我们的 K 必须比它严格更强，否则会被说成"verbosity 换个名字"。

**区别在哪？** 两个都是**比例**（bounded [0,1]），所以**分不清"100 行干净代码"和"10000 行干净代码"**。K 是**绝对描述长度**。一个系统可以整体膨胀 10 倍而 verbosity 不变。这句话要写进论文。

# 族 2：压上下文（不是压代码）

## 4. ACE：压缩会把知识压死 ★★★★★

**【精读】** `2510.04618` · Stanford + SambaNova + UC Berkeley · **ICLR 2026** · 代码 `github.com/ace-agent/ace`

### 一句话

> 大家以为"上下文越短越好"，这篇说**反了**：让模型把笔记"总结成精炼版"，会让笔记**逐轮崩塌**，最后比不总结还差。正确做法不是重写，是**只追加、用确定性逻辑合并去重**。

### 它治什么病

两个词，值得记：
- **brevity bias（简洁偏好）**：优化器天然偏爱"短而通用"的指令，把领域细节、工具用法、常见失败模式都洗掉了
- **context collapse（上下文崩塌）**：靠 LLM 整篇重写来维护笔记，会一轮比一轮短、一轮比一轮空

### 那组必须记住的数字（原文 Figure 2）

| 步 | 上下文长度 | 准确率 |
|---|---|---|
| 第 60 步 | **18,282 token** | **66.7%** |
| 下一步（重写之后） | **122 token** | **57.1%** |
| 完全不给上下文 | — | 63.7% |

**压完比不给还差。** 这不是"压缩有损"，是"压缩摧毁了已经积累的东西"。

### 怎么做（反着来）

不重写，改成**条目化管理**：

| 角色 | 干什么 |
|---|---|
| Generator | 干活，产出轨迹 |
| Reflector | 看轨迹，提炼"哪条对、哪条错" |
| Curator | 把教训写成**结构化条目**（元数据 + 内容） |
| Updater | **不用 LLM**，用确定性逻辑把新条目并进主上下文（grow-and-refine） |

核心是 **delta 更新**：每次只追加一小批条目，合并去重靠**嵌入相似度**，不靠 LLM 总结。

### 数字

| 项 | 值 |
|---|---|
| agent benchmark | **+10.6%** |
| 金融领域 | **+8.6%** |
| AppWorld 榜 | 用开源 DeepSeek-V3.1 **追平**榜首的商业 agent（GPT-4.1 驱动），在更难的 test-challenge 分片上**反超 +8.4%** |
| 适配延迟 | 比 GEPA **−86.9%** |

### 软肋

- 它的立场极端（"上下文应该越长越详细"），只对"长上下文能力强的模型"成立
- 条目化管理本身也要设计 schema，不是免费的

### 我们能拿来干什么

**这是 intro 就必须回应的最强反面证据。**

审稿人一定会问：「你压 harness，ACE 刚证明压缩会自毁。」

**答法**（三步，缺一不可）：
1. **承认**：ACE 说的是"用 LLM 整篇重写会崩"，这个我们完全同意，所以我们**禁止整篇重写**
2. **区分对象**：ACE 压的是**运行时上下文**（模型眼前看到的一切，包括任务本身）；我们压的是**harness 源码**（工具、控制流、提示模板本身）。前者是"这一局要不要记住"，后者是"这个系统怎么写"
3. **给出对应机制**：我们用的是 ACE 说的那条正路——**增量、结构化、确定性合并**，即 AST 级删减 + 行为等价回归，而不是"让模型总结一下"

## 5. ACON：教模型"怎么压"，而不是"压多少" ★★★★

**【精读】** `2510.00615` · KAIST + Microsoft + Cambridge · **ICML 2026** · 代码 `github.com/microsoft/acon`

> ⚠️ **先更正一处**：我上一份文档（`20_...`）写的是"ACON 报历史压缩因 KV-cache 几乎不省钱"。
> 那是 **v1 附录**的说法。**v3（ICML 版）的实测表 4 不是这样**——它省钱，但**明显变慢**。以下是 v3 原文数字。

### 一句话

> 压缩 prompt 的难点不在"压多少"，而在"**压的时候不能丢什么**"。这篇的招是：先看"完整上下文能过、压缩后挂了"的那些成对轨迹，让强模型**反推压缩指南哪里写错了**，改指南，再压。

### 它治什么病

长程 agent 的上下文会无限长，两个后果：**贵**、**被无关信息干扰导致推理退化**。

已有做法各有毛病：
- **手写启发式**：脆，换个环境就崩
- **训模型来压**：对闭源 API 模型不可行

ACON 的定位：**不动模型权重，只优化"压缩指南"这段自然语言。**

### 怎么做

1. 跑一批任务，收集**成对轨迹**：完整上下文成功、压缩上下文失败
2. 强模型分析失败原因 → 提炼"缺了什么信息" → **改压缩指南**
3. 迭代
4. 最后把优化好的压缩器**蒸馏进小模型**，把压缩本身的开销降下来

### 数字

| 项 | 值 |
|---|---|
| 峰值 token | **−26% ~ −54%** |
| 小模型当长程 agent | **最高 +46%**（AppWorld +32%、OfficeBench +20%、8-objective QA +46%） |
| 压缩器蒸馏后成本 | gpt-4.1 $0.045/例 → gpt-4.1-mini $0.014（−69.2%）→ 蒸馏 Qwen3-14B **$0.0004（−99.1%）** |

**但必须一起引的表 4（AppWorld 端到端）**：

| 方法 | API 成本 | 延迟 |
|---|---|---|
| 不压缩 | $0.331 | **73.24s** |
| ACON（压历史） | **$0.285（−13.9%）** | 87.68s（**+19.7%**） |
| ACON（压观察） | **$0.272（−17.8%）** | 101.92s（**+39.2%**） |

**钱省一成多，时间多两到四成。** 这个 trade-off 说得很诚实，但它对我们的意义很明确：

### 我们能拿来干什么

**别把"降成本"当卖点。** 这是这篇给的最大警告。

- 上下文压缩的钱省得很有限（−14%~−18%），因为压缩器自己也要跑
- 想靠"K 降低 → 省钱"立论，会被这张表直接打掉

**正确的卖点**（我在 `20_...` 里也提过，这里更硬了）：
1. **结构可审计**：K 是可复算的字节数，任何人拿源码就能重现
2. **可归因**：see 下一节 HarnessMinimizer 那条 28%→44–51%
3. **可维护**：少一倍的规则就少一半的"改一处不知道会不会崩"

## 6–8. LLMLingua 三连：这一族的基准线

**【精读 LLMLingua / LLMLingua-2；扫读 LongLLMLingua】**

| 论文 | 编号 | 一句话 | 关键数字（原文口径） |
|---|---|---|---|
| **LLMLingua** | `2310.05736`，EMNLP 2023 | 用一个小模型（GPT-2 small / LLaMA-7B）算每个 token 的困惑度与互信息，删"信息量低"的；再加一个**预算控制器**把压缩比分配给不同成分（指令 / 示例 / 问题），并用迭代算法维持语义完整 | **最高 20× 压缩**，性能损失很小。评测集：GSM8K（数学推理）、BBH（推理与 ICL）、ShareGPT（对话）、Arxiv-March23（摘要） |
| **LLMLingua-2** | `2403.12968`，ACL 2024 Findings | 把压缩**改造成"逐 token 二分类"**：用 GPT-4 蒸馏出一个抽取式压缩数据集，训 XLM-RoBERTa-large / mBERT 判"留/删"。好处是**任务无关**、跨域稳 | 压缩器本身比已有方法**快 3–6×**；在 **2×–5× 压缩比**下端到端延迟降 **1.6–2.9×** |
| **LongLLMLingua** | `2310.06839`，ACL 2024 | 在 LLMLingua 之上加**问题感知 + 位置感知**（专治长上下文里"中间的信息模型看不见"），并对文档做重排序 | RAG 端 **+21.4%**，只用 **1/4** token（据摘要与项目主页） |

### 一个必须注意的口径差异

**LLMLingua 的"20×"和 LLMLingua-2 的"2×–5×"不是同一件事：**
- 20× 是**极端档**的最好结果，任务类型有限（主要在摘要 / 对话这类冗余度高的输入上）
- LLMLingua-2 的 2×–5× 是**主实验的常规工作区**，它自己报的加速也是在 2×–5× 下测的

**写论文时别说"LLMLingua 系列普遍能压 20 倍"。** 正确说法是"最高 20×，常用区间 2×–5×"。

### 它和我们的根本区别

**它删的是 token，不是结构。**

LLMLingua 不会告诉你"这五个 if-else 该合并成一个函数"，也不会告诉你"这个防御分支是必要的"。它只是把"这个字不太重要"的字删掉——**删完的文本人读起来是残句**，虽然模型还能懂。

（这一族自己讲得很清楚：压缩后的 prompt 可以不合语法，"capital France known Eiffel Tower Paris" 模型照样懂。**但这不是我们想要的 harness**——我们的 harness 是要给人看、给人改的。）

**所以它是我们的工具，不是我们的对手**：
- 可以当 K 的**补充度量**（"这段 harness 在 LLMLingua 视角下可删多少"）
- 不能替代 K。因为 K 必须是**可复算、人可读、结构不变**的

# 族 3：压代码结构

## 9. CodeTaste：会让模型"改"，但不会让它"找" ★★★★

**【精读】** `2603.04177` · ETH Zurich + LogicStar.ai · **ICML 2026** · 基准站点 `codetaste.logicstar.ai`

### 一句话

> 把重构拆成两件事考：**"给你写清楚要改什么，你改得对吗"**和**"只给你一个大概范围，你自己能找到该改哪吗"**。前者能做（最高 69.6%），**后者只有 7.9%**。

### 它治什么病

重构的定义是"**保持行为的**程序变换"。但 LLM 重构有个隐藏问题：**它可能改得对，也可能改错地方，还可能什么都没发现。**

以前的 benchmark 大多是单文件、单语言，规模小。

### 怎么做

**两个赛道：**

| 赛道 | 给的提示 | 平均长度 |
|---|---|---|
| **Instructed**（指令轨） | 详细描述要做的重构 | 1921 字符 |
| **Open**（开放轨） | 只说"这块有问题，你看看" | **38 字符** |

**开放轨三种推理模式**：Direct（直接改）／Plan（先写计划再改）／Oracle Multiplan（写多份计划，让裁判挑最贴合的再改）。

**评分不用人**：仓库测试套件（功能对不对）+ **定制静态检查**（用数据流推理验证"该删的模式删了、该加的模式加了"）。

### 数字

| 轨道 | 结果 |
|---|---|
| Instructed | IFR 最高 **69.6%**（GPT-5.2）；开源 Qwen3-Coder 只有 10.7% |
| **Open / Direct** | **alignment 只有 7.9%** |
| Open / Plan | 10.7% |
| Open / Oracle Multiplan | 10.1% |

结论：**"先写计划"能小幅改善，"让裁判挑计划"反而没更好。**

### 软肋

- 100 个实例、6 种语言，规模还是偏小
- 它的"对齐"评分依赖静态规则，规则本身的完备性没被单独验证

### 我们能拿来干什么

**这是"压缩算子不能交给模型自由发挥"最硬的一条证据。**

7.9% 意味着：**你让模型自己找"哪里该简化"，它十次里对不了一次。**

所以我们的设计必须是：
- **算子结构化**（删死代码、并分支、提前返回、合并重复——四类各自有明确触发条件）
- **判据外部化**（测试 + 分数 + 覆盖率，不是模型说"我觉得等价"）
- 模型只负责**在给定算子里生成候选**，不负责**决定该不该压**

这条直接支持"四类算子分级 + 高风险算子要更严验证门"的设计。

## 10. REFINE：五道检查之后，仍有 42.9% 的文件丢了关键断言 ★★★★★

**【精读】** `2608.23611` · Tampere University + University of Derby · 2026-08

### 一句话

> 搭一条五段式的多 agent 重构流水线（找坏味道 → 规划 → 改 → 复查 → 报告），在 450 个 Java 文件上跑。**坏味道确实降了 68%~73%，但 42.9% 的文件把 `assert` / `fail` 调用弄没了。**

### 它治什么病

单靠"让 LLM 重构"不可靠。这篇想验证：**加上证据链和多段检查，能不能变可靠？**

### 怎么做

五个环节串起来，每个候选都挂着"为什么改、改完验证了什么、还残留什么风险"。

### 数字（原文表）

| 项 | GPT-5.5 | Gemini 3.1 Pro | Claude Opus 4.8 |
|---|---|---|---|
| 坏味道总降幅 | **68.26%** | **72.79%** | **68.49%** |
| 公开方法签名保留 | 93.3% | 86.2% | 94.2% |
| 异常处理结构保留 | 95.8% | 92.4% | 96.2% |
| 框架契约保留 | 94.4% | 90.4% | 93.3% |
| 条件结构保留 | 90.0% | 86.0% | 87.8% |
| **关键 assert/fail 保留** | **57.1%（三者完全一致）** | 57.1% | 57.1% |
| 完整静态保持代理 | 88.0% | 81.8% | 90.0% |
| 平均删掉的公开方法数 | 0.40 | **1.45** | 0.60 |

**三个模型在 assert 上完全相同（257/450）**——因为这是静态检查的确定结果，不是模型差异。**42.9% 的文件丢了关键断言。**

**重构风格差异极大**：GPT-5.5 改动紧凑；Gemini **删得凶**（净 LOC 降得多，但删公开方法最多）；Opus **提取得多**。

### 作者自己怎么说（这句必须原样引）

> "这些静态检查是**风险证据，不是行为等价性的证明**。"
> "无论直接提示还是多 agent 流水线，**都不足以证明行为被完整保持**。"

### 我们能拿来干什么

**这是我们"三重门 + AST 白名单"的最强外部支持。**

别人做了五段式流水线、加了保持性检查，**仍然有 42.9% 的文件弄丢关键断言**。那我们凭什么说"gzip 变短了就是改进"？

**所以**：
1. 我们的压缩分支必须有"**禁止触碰清单**"（assert / raise / 白名单分支 / 错误处理），而且要在 **AST 层**保护，不能靠提示词叮嘱
2. "行为等价"不能是二值宣称，必须是**分层的**：编译通过 ≠ 测试通过 ≠ 分数不降 ≠ 保持性检查通过
3. 论文里要主动写：**我们的等价判定也是有界的**，给不出"完全等价"的证明——这是诚实，也是防审稿

# 族 4：压"复现 bug 的最小程序"

## 11. HarnessMinimizer：删到 1/5，反而更好诊断 ★★★★★

**【精读】** `2610.23054` · 香港大学 · 2026-10-16

> ⚠️ **名字撞车警告**：这里的 "harness" 是**库 fuzzing 的调用壳**（把随机输入翻译成 API 调用的那段代码），**不是 agent harness**。写论文时千万别混用。

### 一句话

> 一个复杂的 fuzzing harness 崩了，你分不清是**库的 bug** 还是**harness 自己用错了**。把 harness 删到最小复现，**不只是看着舒服——LLM 判断"到底是谁的锅"的准确率从 28% 涨到 44–51%**。

### 它治什么病

最小复现（minimal reproducer）是调试的老办法，但：
- 每次改动都要重新编译、重新跑、重新符号化栈回溯 → **慢**
- 有**数据依赖语句**（这个变量的值来自前面读的文件），删了就变行为 → **删不动**

### 怎么做（三个加速）

1. **复用**：头部分析结果、预构建的库与运行时，不每次重建
2. **记录并重放输入值**：删掉"读取输入"的语句，但把值**补给存活的调用**——这样输入相关的代码能删而行为不变
3. **快速判等**：用便宜方法判断"简化后还崩不崩"，不每次都符号化栈回溯

**背后挂四个成熟归约引擎**：treereduce、**Perses**、WDD 等。

### 数字

| 项 | 值 |
|---|---|
| 规模 | 200 个 crash / 21 个开源库 / 4 个归约引擎 |
| 加速 | 比未优化流水线快 **3.46–4.51×** |
| 体积 | 平均 **1352 token → 143–263 token**（剩 10%–19%） |
| **诊断准确率** | LLM 判断"是 harness bug"：**28% → 44–51%**；判断"是库 bug"：**100% 保持不变** |

### 为什么最后一行最重要

**精简本身提升了可诊断性。** 这是"K 降低"除"省"之外的**第二种收益**，而且这一种没有被 ACON 那张成本表打掉。

**这给了我们一个还没人占的角度**：
> 压缩的价值不在账单，在**让失败可归因**。

如果能把"K 降低 → 归因准确率上升"在 harness 上复现一次，那就是一条独立于成本叙事的贡献。

### 软肋

- 领域是 C/C++ fuzzing，和 agent harness 不同
- 它的 oracle 是**二值**（还崩不崩），便宜确定；我们的 oracle 是**统计的**（通过率、带噪声）→ 这是我们**必须补的一层，也是我们的技术增量**

# 族 5：反方向——让代码变多

## 12. Growing Harness：把重复的判断写成代码 ★★★★

**【精读】** `2609.26760` · 中科院深圳先进院等 · 2026-09-22

### 一句话

> 标准 harness 每一轮都让模型**重新想一遍**"该不该停、JSON 怎么解析、搜索失败了怎么重试"。这篇说：**这些重复的判断应该编译成代码**，模型只做"需要动脑"的部分。结果 **LLM 调用 −76%~−92%，成本 −74%~−99%**。

### 它治什么病

上下文膨胀 + 规模依赖。小模型（4B）一被塞长历史就崩。

### 怎么做

1. 从**无策略脚手架**起步：只有固定的模型/工具接口，**没有任何解题控制器**
2. 失败时生成**函数级执行 DAG**，定位到具体哪个函数坏了
3. 优化器**联合修复一批失败**（不是一次修一个，防过拟合单题）
4. **成功优先的 held-out 门**：如果一串修改伤害了原本能过的题，**整串回滚**
5. 被接受的修改累积进**同一个共享 harness**

### 数字（原文表 1，三次独立评估取均值）

| 基准 / 模型 | Tool-Calling | Growing Harness | 调用数变化 | 成本变化 |
|---|---|---|---|---|
| BrowseComp-Plus / gpt-oss-120b | 40.0% | **49.3%** | 32.7 → **6.0** | $6.70 → **$0.87** |
| BrowseComp-Plus / gpt-oss-20b | **40.0%** | 39.3%（差 0.7pp） | 24.8 → 6.0 | $2.03 → $0.52 |
| BrowseComp-Plus / qwen3.5-4b | 12.0% | **29.3%** | 29.6 → 5.5 | $8.33 → $0.81 |
| WebArena-Verified / gpt-oss-120b | 30.0% | **45.3%** | 26.3 → 3.8 | $2.72 → $0.10 |
| WebArena-Verified / gpt-oss-20b | 12.7% | **44.7%** | 22.3 → 1.8 | $0.39 → $0.03 |
| WebArena-Verified / qwen3.5-4b | 6.7% | **45.3%** | 37.8 → 5.4 | $7.26 → $0.10 |

**最惊人的一行**：WebArena-Verified 上成功率在各规模稳定在 **44.7–45.3%**，而 Tool-Calling 用 4B 模型掉到 **6.7%**。**代码承担了结构，小模型就不需要那么聪明。**

### 软肋

- **它从不报代码规模**。全文搜不到 LOC / 函数数 / 代码体积。它证明"代码变多能降成本"，但**没测"代码多了会不会失控"**
- 训练集 200 题、验证 50、最终 50，规模有限
- 只在两个 web/search 类基准上验证

### 我们能拿来干什么

**这是审稿人一定会拿来打我们的一篇。** 问题会是：

> 「Growing Harness 证明代码越长成本越低（−98%），你压代码不是反着走吗？」

**答法必须区分两种代码**：

| | Growing Harness 长的部分 | 我们删的部分 |
|---|---|---|
| 性质 | **承载控制流**的代码（循环、重试、解析、终止判断） | **不承载控制**的冗余（重复规则、死分支、客套话、防御白名单之外的空检查） |
| 作用 | 把重复推理摊销成确定性逻辑 | 只增加描述长度，不增加能力 |
| 判据 | 调用数下降、成功率上升 | 行为等价 + K 下降 |

**关键**：K 惩罚**必须带防御白名单 + 行为等价门**，就是为了不误伤前一种。这不是口号——我们的对照实验就应该直接量"**被删掉的到底是控制代码还是冗余代码**"。

而且可以反过来说：Growing Harness 恰好证明了**"代码该不该长"是个真问题**——它只说"该长的要长"，没说"不该长的也该长"。它自己缺的那一块，正是我们的位置。

# 补充：两篇"不压代码但必须先看"的

这两篇不是压缩方法，但**它们决定了我们怎么讲"第三维度"**。不看会踩坑。

## 13. HarnessPro：帕累托这件事已经被占了，但占得不完整 ★★★★

**【精读】** `2610.26770` · 清华 + Z.AI + SJTU + Warwick + Kling AI · 2026-10-19 · 代码 `github.com/pzs19/HarnessPro`

### 一句话

> 演化 harness 时**同时看分数和成本**，选出 lite / medium / heavy 三档给不同预算的团队用。**不用标准答案**（label-free），用 LLM 生成的测试当反馈。

### 怎么做

三个角色轮转：**诊断**（看轨迹找失败与可省的开销）→ **规划**（按不同的"性能-成本"偏好出方案）→ **实现**（写成候选 harness）。

选代表点的方法很土但有效：把所有候选按 `(分数, 成本)` 归一化后，用**加权平方距离**在帕累托前沿上挑三个点，对应 lite / medium / heavy。

# 对论文的五条直接结论

## 其一：卖点必须换

**不能卖"省成本"。** ACON 表 4 摆在那里：压缩省 14–18% 的钱，代价是 20–39% 的延迟。审稿人一算就穿。

**要卖"可归因 + 可审计"。** 支点是 HarnessMinimizer 的 28%→44–51%。这条没人反驳得了，因为它是"精简让人更看得懂"这种常识的量化。

## 其二："行为等价"必须分层，不能宣称

REFINE 用五段式流水线、三条静态检查，仍然 **42.9% 的文件丢了 assert**。作者自己写"这不是证明"。

所以我们的表述必须是：
> 一等：编译通过 → 二等：测试套件通过 → 三等：分数不跌出 `S*−δ` → 四等：AST 白名单未被触碰
> **四等都过，才叫"本次删减在该测试集上未观测到行为变化"**——不说"等价"。

## 其三：K 和 verbosity / erosion 的区别要写死

| | SlopCodeBench | 我们 |
|---|---|---|
| 形式 | 比例，bounded [0,1] | 绝对字节数 |
| 分得清"100 行干净"和"10000 行干净"吗 | **不能** | 能 |
| 可复算吗 | 要跑第 137 条 AST-Grep 规则 | 一个 `gzip` 就够 |
| 区分内容来源吗 | 部分（规则里能编码） | **完全不区分** |

**最后一行是我们的软肋，必须主动承认**：K 只是个字节数，它测得到任何内容，但不区分哪些是任务专属。所以抗泄漏这件事，**只能靠 critic，不能靠 K**。

## 其四：δ 必须实打实测，而且要引别人的数

现在有五个团队的量级可以参考：

| 来源 | 噪声量级 |
|---|---|
| Cortex | **−3.3pp**（同 harness 重测） |
| RRSI | **0.4–2.0pp**（分域，占总分比例） |
| SHarP | 3 次平均才敢比 |
| Growing Harness | CI 半宽 11–13pp（50 题规模） |
| SlopCodeBench | 每检查点质量速度 1.3pp |

**注意最后一行的教训**：50 题规模下 CI 半宽就有 11–13pp。**如果我们的实验只有几十道题，δ 会大到什么结论都判不出来。** 这是必须提前算的账。

## 其五：最该补的实验只有一个

**把 HarnessMinimizer 的"精简 → 可归因"在 agent harness 上复现一次。**

因为它同时满足三个条件：
- 不靠成本叙事（不怕 ACON 那张表）
- 有现成的方法谱系（Perses / ddTree / oracle 归约，20 年积累）
- 没人做过（RSI 圈的"剪"全是启发式，删完不跑）

如果这条成立，论文的贡献就从"又一个压缩指标"变成"**压缩让 agent 变得可诊断**"——后者是新的。
