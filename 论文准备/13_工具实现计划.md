# 工具实现计划：从「有一堆能力」到「一条命令出四张表」

2026-11-01 ｜ 对应 `12_工具目标与验收.md`。本文只回答两个问题：**按什么顺序做**、**做到什么算完**。

---

## 〇、一句话

> 把 `14` 的六个能力目标（G1–G6）压成 **四个阶段**，每阶段只有一条硬判据；
> 先做**不烧模型**的两段（S0/S1a），把口径与工具定稿，再开烧钱的两段。

判据不变：**论文里每一个数字，都能追溯到一条命令。**

---

## 一、为什么不能按 G1→G6 顺序做

`14` 的编号是**能力清单**，不是**施工顺序**。按编号做会卡在第一步：

| 假设的顺序 | 会卡在哪 |
|---|---|
| G1 先做（两个 agent 可切） | Terminus-2 强依赖 Docker 容器 + tmux session，Docker 没起就一步都动不了 |
| G6 先做（四张表） | 没有记录 schema，表只能对空数据生成，等于先搭空壳 |
| G3 先做（删测） | 不知道 K 怎么算，删完没法报"K 降了多少"，删测表少一列 |

**正确的依赖链是：记录 schema → K 度量 → 删除 → 判定 → 报告。**
G1 的适配层横跨全程，但它有个"最小可用版本"可以先行。

## 二、四阶段（每阶段一条硬判据）

### S0　度量地基（不烧模型，零外部依赖）

| 项 | 内容 |
|---|---|
| 建什么 | `exp` 包骨架 · 四个核心契约 · 组件切分 · K 度量（radon/tiktoken/gzip）· 静态死组件检测 |
| 覆盖目标 | **G2 全部** + G3 的路线 A + G1 的"组件清单"半边 |
| 硬判据 | 对同一份 harness 连算两次，`组件 → K` 表**逐字节相同**；6 个 agent 里至少 4 个能出完整分解 |
| 不做什么 | 不跑任何模型、不接任何 bench、不碰 Docker |
| 当天可出的东西 | 第一张真表：`Terminus-2 的组件 → K 分解`（实测基线：主文件 619 行，22 个 CC 块，平均 CC 3.41，Halstead V=1020.1） |

**为什么它排第一**：`14` 的门槛写得很清楚——"6 个 agent 都出 K 分解"是 M1 的硬门槛，而 M1 整段不烧模型。
这一段做不完，后面所有表的第三列都是空的。

### S1a　跑通链路（烧少量，无容器）

| 项 | 内容 |
|---|---|
| 建什么 | `local` bench（现有 `tasks/v1.jsonl` 30 题）· 第一个真实 agent 适配（mini-swe-agent，进程内）· `run` 命令 · 记录 schema · `calib` 实测 δ |
| 覆盖目标 | G1 的"一个 agent 跑通" + **G6 的记录半边** + G4 的 δ 来源 |
| 硬判据 | 同一命令跑 3 次，Acc 极差 ≤ δ；随便挑一条记录，能还原出命令 + commit + 配置哈希 |
| 不做什么 | 不做跨 agent 切换、不做双池、不做删测 |

**为什么用 mini-swe-agent 而不是 Terminus-2**：它能在本机进程里跑，不需要容器。
这一步的目的是证明"记录可信"，不是证明"agent 强"。**用弱 agent 验证链路，是正确的选择，不是妥协。**

### S1b　跨 agent 切换（依赖 Docker）

| 项 | 内容 |
|---|---|
| 建什么 | `tb2` bench（容器执行 + pytest 判分）· Terminus-2 适配 · 适配层注册表 |
| 覆盖目标 | **G1 全部**（两个 agent 零改动切换） |
| 硬判据 | 新增第二个 agent **只允许改一个新文件**；`gate` / `run` / 记录 schema 零改动；两个 agent 跑同一道 TB2 题都成功 |
| 前置 | Docker daemon 启动 + `terminal-bench` 装进 venv |

> **这一格是 `14` 的 M0 原文要求，但它有外部依赖。** 处理原则：**S1a 不因 S1b 阻塞而停**，
> 先把不依赖容器的部分做完；Docker 通了立刻补 S1b。

### S2　反事实删测（核心，中等烧钱）

| 项 | 内容 |
|---|---|
| 建什么 | 变体物化（块级删除 + 三道门）· 逐组件删测 · 三态判定 · 防御式白名单 |
| 覆盖目标 | **G3 全部** |
| 硬判据 | 删测表每行带 `删前S / 删后S / 判定 / 证据`；`不可判` 是独立取值且 n 不足时**必然出现**；白名单开关前后"删除建议数"有对比数 |
| 不做什么 | 不做判定器改造、不做报表（那是 S3） |

**为什么删测必须排在判定之前**：删测产出的三态表本身就是判定器的输入素材——
没有"删了不掉分"的样本，判定器无从校准"K 降到多少才算真删"。

### S3　防线与报表（让结果站得住）

| 项 | 内容 |
|---|---|
| 建什么 | 双池 + 运行时拦截 · K 硬否决判定器 · 三维帕累托 · bootstrap 四张表 |
| 覆盖目标 | **G4 + G5 + G6 全部** |
| 硬判据 | 两个构造的假候选（S+0.5/K+30% → 拒；S 不变/K−20% → 收）；演化进程读 quarantine 抛异常；四张表列名与 `10` 第七节一致且每格带 CI 与 run_id |
| 不做什么 | 不做 GUI、不做分布式、不做提示词优化 |

## 四、现状差距：逐项说清「复用 / 重写 / 新建」

现有 `src/` 共 **10,158 行**、**614 个测试**（本轮实测），是 M0 原型。
它的问题不是"写得差"，而是**面向的场景变了**：原来是"改数学智能体的 skill 文本"，现在是"拆别人的 agent 结构"。

| 能力 | 现有资产 | 差在哪 | 动作 |
|---|---|---|---|
| **G1 适配层** | `src/ports/harness.py`（Unit/Edit/apply 契约）· `src/adapters/harness_code.py`（AST 扫函数） | 它是**参数表式**适配：只回答"哪些参数能改"，不回答"agent 怎么跑、怎么重置、怎么观察"。缺 `reset/step/observe` 三件事 | **新建** `exp/adapt/`；`harness_code.py` 的 AST 扫描逻辑并入 `measure/split.py` |
| **G2 K 度量** | `src/domain/kmetric.py`（行数口径 87 行）· `src/domain/complexity.py`（自实现 Halstead/CC/MI 218 行） | 缺 radon 主口径、缺 tiktoken、缺 gzip 压缩率、缺**六类组件切分** | **新建** `exp/measure/`；complexity 作为 radon 的**交叉校验**保留 |
| **G3 删除** | `src/domain/detector.py`（死代码检测 728 行 / 9 类检测器）· `src/domain/prune.py`（只覆盖 5 段 skill 文本） | 缺"组件级 + 物化删除 + 真跑 + 三态"；缺运行时覆盖采集 | **复用** detector（README 已验：自扫描 6→4 条，4 条全真阳性）· **新建** `exp/remove/` |
| **G4 判定** | `src/domain/gate.py`（三维帕累托 + δ 双地板 281 行） | `kappa1=0.5` 意味着 **S 涨 10pp 可让 K 涨 60%** → K 仍可被买通。`14` 的假候选 S+0.5/K+30% 走现有代码：`dK=0.30 < 0.10+0.5×0.5=0.35` → **会被接受** | **重写** `exp/judge/gate.py`；旧 gate 保留作对照臂 |
| **G5 双池** | `src/domain/sample_pool.py`（失败样本池，版本冻结 219 行） | 那是"失败样本"，不是"数据集池"；没有运行时拦截 | **新建** `exp/judge/pools.py`；sample_pool 不动（它是另一件事） |
| **G6 报告** | `src/domain/report.py`（timeline/kpi 报告 228 行）· `src/domain/stats.py`（bootstrap/CI 166 行，**零外部依赖**） | 缺四张表的形状；缺"每个数字带 run_id" | **复用** stats · **新建** `exp/report/` |
| 记录 schema | `src/domain/ledger.py` + `dataset.py` | `unit_id` 恒为 `skill::body`，没组件粒度 | **新建** `exp/run/record.py` |

**复用策略（关键决定）**：`exp` **不复制** `src` 的代码，通过单一文件 `exp/reuse.py` 集中引用。
理由：复制会造成两份实现悄悄分叉（这个坑在 `prototype/simplify` 上已经踩过一次，靠 `sync_check.py` 兜的）。
一个文件收口，将来迁移只需改一处。

## 六、把判据翻译成测试（自证清单）

`14` 的每条判据都要有一条能跑的测试，否则"达标"只能靠嘴说。

| 判据出处 | 测试文件 | 断言什么 |
|---|---|---|
| G1 换 agent 不改主流程 | `test_adapter_zero_change.py` | 注册一个假 agent（单文件）→ `run` 与 `gate` 的源码哈希不变，且能跑完一题 |
| G2 K 可复算 | `test_k_reproducible.py` | 同输入两次 → `KVector` 全字段相等；换 encoding → 差异被写进 manifest |
| G3 三态 | `test_three_state.py` | n=3 且 ΔS 落在噪声内 → 判定必须是 `undecidable`，**不得是 `delete`** |
| G3 删除可复跑 | `test_mutate_gates.py` | 同一 `locator` 删两次 → 变体源码逐字节相同；删出语法错误 → 拒且标记 `unrunnable` |
| G4 K 单独否决 | `test_judge_k_veto.py` | 构造 S+0.5/K+30% → `reject`；S 不变/K−20% → `accept` |
| G4 δ 可复现 | `test_delta_measured.py` | δ 结构里必须带 `n_repeat / spread / measured_at`，缺一即失败 |
| G5 池隔离 | `test_pool_guard.py` | evolve 模式下 `bench.tasks(pool="quarantine")` → 抛 `PoolViolation` |
| G6 四张表 | `test_tables.py` | 列名与 `10` 第七节逐字一致；每行含 `run_id`；缺 `undecidable` 取值 → 失败 |
| 记录可追 | `test_record_lineage.py` | 任取一条记录 → 能解析出 argv、commit、配置哈希、工具版本 |

**这 9 条测试就是"工具成熟度"的唯一证据。** 没写这 9 条之前，任何一个 G 都只能算"写了代码"。

## 七、风险与停手信号

| 风险 | 触发条件 | 处置 |
|---|---|---|
| K 口径改一次，历史数据全废 | S0 定稿后又想改主口径 | 主口径只在 S0 定一次；之后只加"补充口径"，写附录 |
| 删除把活组件判死 | S2 中"删了 → S 掉超 δ"的组件里，有超过 1/3 是静态判定的死组件 | 停，修检测器（判定过激），不要继续删 |
| 不可判被当成无用 | 三态表里 `undecidable` 占比 > 70% | 不是工具问题，是 n 太小；先算 `mde(σ, n)` 报告能检测的最小效应，再决定加不加 n |
| K 降不下来 | S3 主实验里所有 agent 的 K 都降 < 2% | 回 S0 查组件切分：大概率漏了最占体积的那一类 |
| Docker 长期不通 | S1b 排不进去 | 不阻塞主线：用 mini-swe-agent 在 local bench 上把 S2 做完，TB2 留到最后补；论文里如实写"主实验场地" |
