# 简化的判据：什么能删、什么能简化、什么该重写

2026-11-02 ｜ 依据 14 篇论文 + 本项目实测

> 这份文档只回答一件事：**凭什么说这段代码"可以动"**。
> 方法（怎么动）在 skill `代码简化` 里；判据（凭什么动）在这里。

---

## 0. 统一标准：每个改动都必须有"担保物"

**这是全文唯一的一条总纲。**

任何一次简化，都要能回答一句话：

> **"我怎么知道改完没变坏？"**

答案必须是**一个可执行的东西**，不是"我看了觉得一样"。这个"东西"就是担保物。

| 你面对的问题 | 判据 | **担保物** | 静态能识别吗 |
|---|---|---|---|
| **能删吗** | 删除后观测不到差异 | 引用计数 / 触达统计 / 消融 | ✅ 前两层能 |
| **能简化吗** | 存在语义等价的更短表示 | **差分测试** | ✅ 能（AST 模式） |
| **逻辑差吗** | 控制流复杂度 ≫ 问题本身复杂度 | 测试固定行为 + 结构重构 | ⚠️ 半能 |
| **算法差吗** | **实测在这个输入规模上慢** | **profile + 基准测试** | ❌ **不能** |

**四类问题的担保物强度递增，识别手段完全不同。** 用错手段就会空转——
这就是"简化效果不理想"的结构性原因（详见 §8）。

**没有担保物的改动，一律不许做。** 这条比下面所有细则都重要。

## 1. 能删的标准：三层，担保物逐层变强

### 1.1 三个层级

| 层 | 判据 | 担保物 | 可信度 | 成本 | 收益 |
|---|---|---|---|---|---|
| **L1 零引用** | 名字在整个作用域内无引用 | 引用计数 + 导入图 | 低（易漏动态派发） | 极低 | 小 |
| **L2 零触达** | 跑 N 次，从未被执行 | 覆盖率 / `sys.monitoring` | 中 | 中 | 中 |
| **L3 零贡献** | 执行了，关掉后分数/输出不变 | **单模块消融** | **高** | **高** | **大** |

**注意箭头方向**：可信度、成本、收益**同向递增**。所以：
- 便宜的先做（L1），但别指望它有效果
- 值钱的要花代价（L3），而且**L3 只能"关"，不能"删"**

### 1.2 为什么 L3 不能删

L3 的定义是"执行了但没起作用"。它**有调用者**，删了会 `NameError`。
所以 L3 的正确动作是：**加开关关掉**，跑完验收，再决定要不要删**调用点**。

SHarP 剪掉 24/27 个模块后分数还涨了——它剪的是**模块开关**，不是删代码。
**这个区别必须记住**：删代码是 L1/L2，关模块是 L3。

### 1.3 L1 的五个陷阱（判"零引用"时必须逐个排除）

`grep` 只出现一次 ≠ 可以删。必须排除：

| 陷阱 | 检查方法 |
|---|---|
| **导出契约** | `__all__`、`__init__.py` 的 re-export |
| **动态派发** | `getattr` / `globals()` / 字符串拼接的函数名 |
| **框架契约** | 装饰器注册、pytest fixture、`entry_points`、CLI 命令名 |
| **鸭子类型** | `Protocol` / 抽象基类的实现方法 |
| **测试引用** | 只在 tests 里被用的，删了要连测试一起删（或这就是它存在的理由） |

> 本项目实测：`detector` 已处理前四项（`_has_dynamic_features` / `_protocol_names` / `_exported_names` / `_dynamic_dispatch_files`）。
> 但 11 条候选里仍有 10 条是误报——**误报不在"零引用"这一层，在"零引用所以无用"这个推论上**（见 §7）。

## 2. 能简化的标准：三件套缺一不可

### 2.1 判据

一段代码"能简化"，当且仅当**同时满足**：

| # | 条件 | 反例（不满足） |
|---|---|---|
| ① | **能匹配到一个具名算子**（R1–R20 / P1–P8） | "我觉得这里可以更短" |
| ② | **能写出一句"为什么等价"** | "看起来一样" |
| ③ | **差分测试 100% 一致** | "单测还过" |

**为什么必须具名**：CodeTaste 实测——让模型"自己找该改哪"，对齐率 **7.9%**；
把"要改什么"说清楚，**69.6%**。**具名算子就是"说清楚"的工程化形式。**

### 2.2 "等价"要写成可检验的句子

不是"这两段等价"，而是：

> **因为** `x` 在循环体内未被修改，**所以** `for i in range(len(x))` + `x[i]`
> 与 `for i, v in enumerate(x)` 对所有输入产出相同的序列。

模板：**`因为 <某条件成立>，所以 <两个版本在所有输入上输出相同>`**。

写不出这句，说明**等价性依赖一个你没验证的前提**——那就是赌。

### 2.3 差分测试是唯一的强验证

```
对同一批输入 I（旧测试 + 边界值 + 随机 + 运行日志里的真实输入）：
    逐条比较 f_old(i) == f_new(i)
要求 100% 一致
```

**为什么单测不够**：单测是**为旧实现写的**，它可能根本没覆盖你动的那段。
REFINE 用五段流水线 + 三条静态检查做重构，仍有 **42.9%** 的文件把关键 `assert` 弄没了——**而测试照样过**。

## 3. 逻辑差的标准：控制流复杂度 ≫ 问题复杂度

这一类**不是冗余**，是"写得比问题本身绕"。判据不是"看起来乱"，是下面四个信号。

### 3.1 四个识别信号

| 信号 | 怎么量 | 含义 |
|---|---|---|
| **分支在描述数据形状，不是在表达策略** | CC 高，但业务规则条数少 | 该用表/多态，不是该拆 |
| **嵌套深但条件互斥** | 嵌套 ≥3 层，且各层条件互不依赖 | 可以扁平化（R3 卫语句） |
| **同一个概念有三种写法** | 同一语义在多处用不同表达式 | 该统一，不是该删 |
| **命名不承载语义** | `data` / `tmp` / `flag` / `_x` / `ret` | 零风险改名 |

### 3.2 修法：严格按风险递增做

| 步 | 动作 | 风险 | 需要担保物吗 |
|---|---|---|---|
| 1 | **改名** | **零** | 不需要（编译器保证） |
| 2 | 提取函数（不改控制流） | 低 | 单测 |
| 3 | 早返回 / 卫语句 | **中**（条件有依赖就不行） | 单测 + 差分 |
| 4 | 表驱动 | 中高 | **差分测试必做** |
| 5 | 参数化 / 抽象 | **高** | 差分 + 逐段单测 |

**第 1 步的价值被严重低估**：改名零风险、零副作用，而它解决的是"读不懂"问题的一大半。

### 3.3 什么情况下"乱"是对的

不是所有高 CC 都该动。反例（本项目真实）：

`planner._validate`，65 行、CC=27，八个检查串成链：

```python
for c in cards:
    if not isinstance(c, dict):          skipped.append(...); continue
    seg = ...
    if seg not in idx:                   skipped.append(...); continue
    if seen.get(seg, 0) >= 2:            skipped.append(...); continue
    if action not in ACTIONS:            skipped.append(...); continue
    ...
```

看着非常该"表驱动化"。**但不能改**：

- 八个检查**依赖不同**（第 3 个用第 2 个算出的 `seg`）
- **副作用不同**（`seen` / `seen_mode` 计数）
- **失败原因都是给人看的**

压成 lambda 表，等价性风险高、可读性倒退。

**真该动的是**：把 8 处重复的 `skipped.append({...})` 抽成一个 `_skip(seg, why)`——
**去掉重复字面量，不动控制流**。

> 这是"逻辑差"和"冗余"的分界线：**重复的是字面量 → 抽取；重复的是结构但语义异质 → 不动。**

## 4. 算法差的标准：唯一判据是 profile

### 4.1 先说结论：静态扫描识别不了算法问题

本项目实测：用 AST 扫"循环内线性查找 / 循环内重复计算 / 嵌套循环"等模式：

```
可疑 213 处
  A3 循环内重复 len()     72
  A4 嵌套 for             69
  A3 循环内重复 sorted()  42
  A1 循环内 in 字面量列表  16
  A3 循环内重复 list()    14
```

**抽样核查：全部误报。**

| 样本 | 实际代码 | 为什么不是问题 |
|---|---|---|
| `len(out) >= MAX_UNITS` | `out` 每轮追加 | len 必须每轮重算，正确 |
| `for code, rows in sorted(by_code.items())` | for 头部 | **只求值一次**，不在循环内 |
| `fname not in ('getattr','setattr')` | 2 元组 | 常量元组，O(1) |
| `kind in ('ActionEvent','ObservationEvent','AgentErrorEvent')` | 3 元组 | 常量元组，O(1) |

**原因**：判断"是不是不变量"需要**数据流分析**（这个变量在这轮里变没变），语法匹配做不到。
**所以算法层的静态告警，信噪比接近 0。**

### 4.2 正确判据：三条同时成立才动手

| # | 条件 | 怎么验 |
|---|---|---|
| ① | **profile 显示它是热点** | `cProfile` / `py-spy`，看累计耗时占比 |
| ② | **输入规模能达到复杂度临界点** | 看 n 的**来源** |
| ③ | **换算法后的常数因子不抵消收益** | 基准测试实测 |

**第 ② 条最容易被跳过，也最关键。** n 的上界由**输入来源**决定，不由代码决定：

| n 的来源 | 典型上界 | 值不值得优化 |
|---|---|---|
| 模块内常量列表 | 5–20 | **不值得**（O(n²) 也是微秒级） |
| 配置项 / 变量表 | 20–30 | 不值得 |
| 一个文件的行数 | 10³–10⁵ | **值得** |
| 一批文件 / 仓库全部文件 | 10²–10⁴ | 值得 |
| 用户输入 / 外部数据 | **不可控** | **必须**按最坏情况设计 |

**临界点参考**（Python 量级）：

| n | O(n²) 操作数 | 大致耗时 | 结论 |
|---|---|---|---|
| 10 | 100 | ~10 μs | 别动 |
| 1,000 | 10⁶ | ~0.1–1 s | 该看 |
| 10,000 | 10⁸ | ~10–100 s | 必须改 |
| 100,000 | 10¹⁰ | 不可接受 | 必须改 |

### 4.3 修法：基准驱动，不是测试驱动

```
1. 写基准（记录当前耗时 / 内存）
2. 改实现
3. 基准验收：必须显著更快，否则回退（因为新实现通常更难读）
4. 单测 + 差分测试确认行为不变
```

**注意顺序**：算法改动的验收是**基准跑第一，单测跑第二**。
因为单测只证明"没坏"，不能证明"变快了"。**改完没变快 = 白改，还多了复杂度。**

### 4.4 五类真实的算法问题（遇到再改，不要预防性改）

| 形态 | 典型修法 | 前提 |
|---|---|---|
| 双层循环里做线性查找 | 先建 `set` / `dict` 索引 | n 可达 10³+ |
| 循环内重复计算不变量 | 提到循环外 | 被提的表达式无副作用 |
| 反复 `list.index` / `in list` | 换 `set` 或 `dict` | 容器大且查得多 |
| 递归无记忆化 | 加 `lru_cache` 或改迭代 | 有重叠子问题 |
| 循环内字符串拼接 | `''.join(...)` | **需实测**（CPython 的 `+=` 有优化，未必慢） |

**最后一条要特别注意**：`s += x` 在 CPython 里对 str 有就地优化，**未必是 O(n²)**。
这就是为什么**必须 profile，不能凭印象**。

## 5. 清晰 vs 高效：怎么取舍

两者会冲突。判据只有一条：

> **96% 的代码不是性能瓶颈。非瓶颈处一律选清晰。**

| 位置 | 选什么 | 附加要求 |
|---|---|---|
| **非热点**（profile 里看不见） | **清晰** | 无 |
| **热点** | 高效 | **必须**：封成有名字的函数 + 注释说明"为什么这样写" + 保留基准数据 |
| 热点且优化后极难读 | 高效 + 详细注释 | 考虑写一个清晰版作为文档，测试比对两者一致 |

**禁止**：为了"可能的"性能牺牲可读性（premature optimization）。
判断"可能"的唯一方法是 **profile，不是直觉**。

## 6. 决策树（动手前走一遍）

```
这段代码有问题吗？
│
├─ ① 有没有调用者？
│   └─ 无 → 查五个陷阱（导出/动态派发/框架契约/鸭子类型/测试）
│         └─ 全排除 → 【删】（L1，收益小，别期待效果）
│
├─ ② 有调用者，但跑起来从没执行过？
│   └─ 是 → 【删】（L2，覆盖率证明）
│
├─ ③ 执行了，但关掉它分数/输出不变？
│   └─ 是 → 【加开关关掉】（L3，不是删；要消融 1+m 次）
│
├─ ④ 写法比问题本身绕？
│   ├─ 能匹配 R1–R20 某条 → 写出等价条件 → 差分测试 → 【改写】
│   └─ 匹配不上（如异质校验链） → 【不动】，最多抽重复字面量
│
├─ ⑤ profile 显示它是热点，且 n 能达到临界点？
│   └─ 是 → 记录基准 → 换算法 → 基准验收 → 【优化】
│
└─ ⑥ 只是"看着不顺眼"？
    └─ 【不动】。或者做零风险的那件事：改名
```

**六个出口，只有 ④⑤ 会产生"改进"，①② 是卫生，③ 需要大成本，⑥ 是陷阱。**

## 7. 负例：四种"看着该简化"但其实不能动

| # | 看起来 | 为什么不能动 | 证据 |
|---|---|---|---|
| **N1** | `def records(self): return list(self)` 该内联 | 命名包装**承载语义**，调用处 `records()` 比 `list(self)` 可读 | 本项目 11 条候选里 7 条此类型 |
| **N2** | 两个类里同名的 2 行 property 该合并 | 鸭子类型的自然产物，合并要抽基类 → **引入耦合** | 11 条里 3 条此类型 |
| **N3** | 异质校验链该表驱动化 | 依赖不同 / 副作用不同 / 原因给人看 | `planner._validate` |
| **N4** | 常量元组成员判断（`in ('a','b','c')`）是 O(n) 查找 | **Python 对常量元组有优化**，且 n=3 | 16 处抽样全误报 |

**共同点**：它们的"冗余"是**表面相似**，不是**语义重复**。
区分方法只有一个：**能不能写出那句话**。"因为 X 所以等价"——写不出，就是表面相似。

## 8. 用这套判据看我们自己的代码：优先级重排

把四类判据套到本项目的两个对象上：

| 对象 | 能删（L1/L2） | 能简化（R1–R20） | 逻辑差 | 算法差 |
|---|---|---|---|---|
| `src/` 工具（26k 行） | 35 行 / 0.1% | 4 处 / ~31 行 | 57 个 CC>10 函数，多数是**异质分支，不该动** | **未 profile，无结论** |
| `worktree` SDK（100k 行） | 2,483 行 / **2.98%** | 未扫 | 未测 | 未 profile |

**四条判断**：

1. **`src/` 的代码层已经没什么可做**——四类加起来不到 100 行。继续在这里投入是浪费。
2. **`worktree` 的删除空间大 30 倍**，但那 2,483 行是 L1（零引用），**预期效应为 0**，只能当卫生。
3. **真正的改进在 L3**（有触达零贡献），而它需要消融：`1 + m` 次 × 30 题。
4. **算法层目前没有任何证据**——我们没 profile 过。**在 profile 之前，"这段代码慢"全是猜测。**

## 9. 一句话

> **判据不是"这段代码看起来怎么样"，是"我拿什么担保它改完没变坏"。**
> 能删的靠引用计数，能简化的靠差分测试，逻辑差靠结构度量，算法差靠 profile。
> **四种担保物不能互换——用错一种，就会在一片本来没问题的地方空转。**
