# 我们该怎么简化代码：基于 14 篇论文的分析（修订版）

2026-11-02 ｜ 依据 `21_论文精读` / `22_经验综合` / skill `代码简化`

> **修订说明（重要）**：初版把 `src/`（2.6 万行的测量工具）当成了简化对象，得出"可删只有 0.1%"的结论。
> 复盘 `git log` 后发现**真正的对象是 `third_party/worktree`（OpenHands SDK，10 万行）**——
> T14 已经在它上面删过 877 行。两者可删空间差 **30 倍**，结论完全不同。本文按正确的对象重写。

---

## 0. 三句话

1. **两个对象，两种命运**：工具 `src/` 可删 0.1%（人设计的，冗余被管住了）；被测 harness 可删 **2.98%**（第三方 SDK，被反复 patch 长的）。
2. **T14 已经做过一次，删了 877 行，但选错了观测量**：删的是"grep 只出现 1 次"的零引用函数——**这类函数删了，通过率本来就不该变**。所以"没效果"是预期结果，不是失败。
3. **下一刀不是删更多，是换指标**：代码删除的收益不在通过率，在**可归因性**（实测 28%→44–51%）与**规模**。

---

## 1. 先纠正对象：30 倍的差距

| | `src/`（测量工具） | `third_party/worktree`（被测 harness） |
|---|---|---|
| 规模 | 153 py / **26,011 行** | 410 py / **100,091 行**（T14 时 313 / 83,091）|
| 可删候选 | 11 条 / **35 行 / 0.1%** | 167 条 / **2,483 行 / 2.98%** |
| 逻辑重复（生产） | 2 组 / 29 行 | 未测 |
| 谁写的 | 我们，分层设计（domain/ports/usecases/adapters） | 第三方 SDK，被上游反复 patch |
| 该用什么判据 | 重构（无分数，B 版门） | 压缩（有分数，A 版门） |

**30 倍的差距不是偶然。** 它恰好印证了 SHarP 的前提：

> 那 4 个 harness 能剪掉 24/27，因为它们是 *"iteratively refined by amending and patching"* —— **被补丁喂大的**。

**我们的工具是设计出来的，SDK 是迭代出来的。冗余只长在后者身上。**

所以初版"这库没油水"的判断，只对 `src/` 成立，对真正的对象不成立。

---

## 2. T14 做了什么，以及为什么"看不出效果"

### 2.1 它的设计是对的

`git show b22b78e`：

```
基线 output/calib_v1：跑 .venv 里的 openhands（未改）
实验 output/t14_main：PYTHONPATH 前置 third_party/worktree（删 877 行）
两边同一个 skill、同一个 30 题任务集、同一模型

为什么 PYTHONPATH 能生效
openhands 是 namespace package（无 __init__.py），worktree 置于 sys.path 首位后
openhands.sdk.__file__ 指向 worktree——否则删 worktree 对运行毫无影响，实验就是自欺。
```

**这一段是整个项目里最专业的一次实验设计**：单变量、且**先证明了干预真的生效**（否则就是自欺）。
对照 REFINE 那 42.9% 的教训——大部分"重构研究"根本没验证改的东西有没有被用上。

### 2.2 但它选错了观测量

删的是：*"取其中 grep 全文只出现 1 次（零引用）的 67 个函数 = 877 行"*。

**于是产生一个逻辑闭环**：

```
如果这些函数真是零引用 → 它们不参与任何执行 → 删了通过率必然不变
如果通过率变了         → 说明它们不是零引用 → detector 判错了
```

**无论哪种结果，都不能证明"简化有收益"。** 这是一次**卫生实验**（hygiene），不是**改进实验**（improvement）。

用 SHarP 的话说：它做的是第 1 步（删零触达），**而零触达的定义就决定了效应为 0**。

### 2.3 而且 n 根本不够

| 项 | 值 |
|---|---|
| 任务数 | 30 |
| 重复 | 4 rep（121 个 run 目录 ≈ 30×4）|
| N | 120 |
| **CI 半宽（0.98/√N）** | **8.9pp** |

**删 1.06% 的零引用代码，期望效应远小于 8.9pp。** 这个实验在统计上判不出任何东西——
**即使真有效应，也会被噪声淹没。**

### 2.4 结论

> **T14 的"零结果"是正确的零结果。** 它证明了"删零引用函数不影响 agent 表现"——这本身是个有价值的卫生结论，
> 但它**不能**用来回答"简化代码有没有用"。

## 3. 按论文，代码简化分三层，每层的效应量和成本完全不同

这是整份分析的核心。**把三件事混在一起做，就会一直得到"没效果"。**

| 层 | 删什么 | 怎么找 | **预期效应** | 验证成本 | 论文依据 |
|---|---|---|---|---|---|
| **L-a 卫生** | 零引用函数 / 未用导入 / 不可达分支 | grep + AST | **0**（本来就不参与执行） | 1 次全量跑 | SHarP 第 1 步 |
| **L-b 改进** | **有触达、零贡献**的模块 | **单模块消融** | 可能正、可能负、可能为 0 | `1 + m` 次评测 | SHarP 第 2 步 |
| **L-c 结构** | 重复块 / 枚举链 / 长函数 | 算子匹配（R1–R20） | 中（可读性、可维护性） | 差分测试 + 单测 | Perses / CodeTaste |

**T14 做的是 L-a，却用 L-b 的指标（通过率）去验收。** 这就是错配。

**L-b 才是"简化有没有用"的战场，而它的成本是**：

```
167 个候选 × 30 题 × 3 次重复 = 15,030 次 trial
```

按 T14 的规模推算，这是**几十倍于当前实验量**的投入。**这是必须先算清楚的账。**

---

## 4. 真正的收益不在通过率——这是最该改的一条

### 4.1 三条论文证据

| 证据 | 数字 | 含义 |
|---|---|---|
| **HarnessMinimizer** | LLM 判断失败归因的准确率 **28% → 44–51%**（库 bug 判断保持 100%） | **精简提升可诊断性**，这是独立于性能的收益 |
| **ACON** | 成本 −13.9%，延迟 **+19.7%** | 省钱会被别的代价吃掉，别只报钱 |
| **SHarP** | 删掉"终止判定"后 **token 反升**；两个配置比全量更贵 | 成本与体积**不同向** |

**合起来一句话**：**代码删了，钱不一定省，但"看得懂"一定提升。**

### 4.2 所以指标要换

| 指标 | 对 L-a | 对 L-b | 现在有吗 |
|---|---|---|---|
| 通过率 | 预期 0（别测） | 主指标 | ✅ |
| **token / 步骤数** | 可能微降（import 快） | 可能升（见 SHarP 反例） | ✅ 有 |
| **可归因性**（失败能否快速定位） | **可能升** | **可能升** | ❌ **没测过** |
| **代码规模** | 直接降 | 降 | ✅ |
| **改动局部性**（改一个功能碰几个文件） | 降 | 降 | ❌ 没测过 |

**最值得补的是"可归因性"**：对 30 题里失败的那些，让模型判"是 SDK 的 bug 还是 skill 写错了"，
比改前改后的准确率。**这是 HarnessMinimizer 那条路在 agent 上的直接复现，而且没人做过。**

## 5. 具体该怎么做：三步，顺序不能换

### 第 1 步｜把 L-a 做完，但**改指标验收**

**做什么**：167 个候选里剩下的 1,606 行（2,483 − 877）继续删完。

**但验收标准换成**：

| 指标 | 判据 |
|---|---|
| 语法 | 313/410 文件 `ast.parse` 全过 |
| 单测 | 全过 |
| **可归因性** | 失败归因准确率**不下降** |
| 通过率 | **预期不变；变了说明 detector 判错，要查** |

**关键**：通过率"没变"是**成功**，不是失败。这句话要写进报告，否则每次都会被误读成"没用"。

### 第 2 步｜才开始 L-b（这是唯一能回答"有没有用"的一步）

**依据**：SHarP 的单模块消融——只需 `1 + m` 次评测，不是 2^m。

**但要先算账**：

```
m 个候选 × 30 题 × k 次 = 总 trial 数
若 m=20、k=3 → 1,800 次；按当前单次成本估，是否可承受？
```

**若不可承受，降级方案**（按性价比）：

1. **只消融"top-k 大模块"**（比如 5 个最大的），m 从 167 降到 5 → 450 次
2. **用更便宜的任务集做消融**（10 题筛选，30 题确认）
3. **优先消融"规则类"而不是"工具类"**（改起来便宜，回滚容易）

### 第 3 步｜L-c 只在被 L-b 选中之后做

**依据**：CodeTaste——"说清楚要改什么"69.6%，"自己找"7.9%。
**所以**：L-c 不许开着一个"去找哪里能简化"的循环，必须**先由 L-b 圈定模块**，再在模块内用 R1–R20 改写。

## 6. 三条反直觉的结论

### 一｜零引用删了没效果，这才是对的

我们已经论证：零引用函数不参与执行，删它不影响任何行为。
**所以 T14 的零结果不是失败，是"detector 判对了"的证据。**

**但它也宣告了一条路的天花板**：靠 grep 找零引用，永远只能做卫生，做不出改进。

### 二｜"有触达、零贡献"才是金矿，而它必须靠消融才找得到

SHarP 剪掉 24/27 靠的不是引用计数，是**逐个关掉跑一遍**。
那 24 个模块**都有人调用**，只是调用了没起作用。

**这正是 SDK 里最可能藏冗余的地方**（100k 行、上游反复 patch、大量兼容层与防御分支）。
**而它一条都 grep 不出来。**

### 三｜CC 高 ≠ 该简化（`planner._validate` 的反例）

我们工具里有个 65 行、CC=27 的函数，八个检查串成链。看着很该"表驱动化"。

**但不能改**：八个检查依赖不同（第 3 个用第 2 个算出的 `seg`）、副作用不同（`seen` 计数）、
失败原因都是给人看的。压成 lambda 表，等价性风险高、可读性倒退。

**真该动的是把 8 处重复的 `skipped.append({...})` 抽成一个 `_skip(seg, why)`**——去掉重复字面量，不动控制流。

**这是 N 类负例的典型**：看着像冗余分支，其实是异质校验链。

---

## 7. 一句话

> **代码简化分三层：卫生（删零引用，效应 0，别用通过率验收）、改进（消融找零贡献，效应有但贵）、结构（改写，效应在可读性）。**
> **把第一层用第二层的指标去验收，就会永远得到"没效果"。**
