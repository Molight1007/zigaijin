# 一、docstring 的定义：标准说的是什么

## 1.1 规范定义

PEP 257 原文的定位是"**a string literal which appears as the first expression in a module, function, class, or method definition**"，它会被绑定到该对象的 `__doc__` 属性。

关键在"绑定到 `__doc__`"这一句。它带来四个后果，也定义了 docstring 唯一的存在理由：

| 后果 | 谁受益 | 本项目用了吗 |
|---|---|---|
| 编译后**保留**在 `__doc__` 里（注释被丢弃） | `help()` / `inspect.getdoc()` | ❌ 全仓 0 处 |
| 编辑器**悬浮提示** | 正在读这个文件的人 | ✅ 这是唯一在生效的 |
| `doctest` 可**执行** | 自动回归 | ❌ 0 处 |
| 文档生成器可**提取** | Sphinx / mkdocs | ❌ 无配置 |

**所以 docstring 的规范用途只有一个：告诉调用者"这东西是什么、怎么调、返回什么、抛什么"。** 也就是**接口契约**。

它和注释的分界线也就清楚了：

```
注释  = 写给"正在改这行的人"，编译后消失
docstring = 写给"要用/要改这个对象的人"，编译后仍在 __doc__
```

## 1.2 但本项目的 docstring 不是这个

实测（`src/` 全部 890 段 / 4,499 行）：

| 风格 | 段数 | 行数 | 占比 |
|---|---|---|---|
| Google（`Args:` / `Returns:`） | **0** | **0** | **0.0%** |
| NumPy（`参数` + `----` 下划线） | 2 | 41 | 0.9% |
| Sphinx（`:param:`） | 0 | 0 | 0.0% |
| **无任何标准结构** | **888** | **4,458** | **99.1%** |

那 2 段里还有一段是 `cli.py` 的模块级 docstring 因为含"用法"小节被误匹配。**真正符合契约格式的只有 `kmetric.k_by_component` 这一处。**

抽样看实际内容，全是这样的：

> `param_edit.py`（22 行）：`## 为什么需要这一层` —— `hypothesis.propose()` 早就会提 `set_param`，`varplan` 也能把变量变成 OpenHands 的真参数——**但中间没有执行者**……

> `cli.py`（21 行）：`存在的理由：run_m0_round() 是纯函数……在此之前，整套实验靠临时脚本驱动，仓库里复现不出任何一条数据`

**这是 ADR（架构决策记录），不是 API 文档。**

## 1.3 为什么会写成这样

不是写的人乱来，是**结构性逼出来的**：

- `docs/` 里没有 ADR 目录，只有 `资料文档/`（调研与汇报）
- 没有任何机制会把 `docs/` 的内容送到正在改代码的人眼前
- 而 docstring 有 IDE 悬浮 —— **这是全项目唯一"一定被下一个人看到"的位置**

**换句话说：docstring 被当成了 ADR 的收容所。** 这解释了一件事：为什么删它"就是真丢知识"——因为**别处真的没有**。

# 二、三个问题逐个回答

## Q1：为什么要放在工具里面？

**分类回答，四类东西答案完全不同。**

| 类型 | 该不该在里面 | 判据（一句话） |
|---|---|---|
| **A 接口契约**<br>`Args/Returns/Raises` | **必须在** | 除了它，没有第二个位置能同时被 `help()`、IDE、doctest 读到 |
| **B 就地约束**<br>"不要用 returncode 判，会污染成 1" | **必须在** | 读者是**正在改这个函数的人**，他在编辑器里，不在浏览器里 |
| **C 设计理由**<br>"为什么需要这一层" | **不该在** | 读者是**想知道系统结构的人**，他读 docs，不读函数体 |
| **D 论文证据 / 实测数字**<br>"SHarP 剪了 24/27" | **不该在，且危险** | **会过期**。论文改版、实验重跑，代码里的数字就变成谎言 |

**B 和 C 的区别是这一节最要紧的一条：**

- **B 是"改之前必须知道"** → 不放在手边就会踩坑 → 必须留，但要压到 3 行内
- **C 是"想知道为什么当初这么定"** → 不在手边也不影响改对 → 可以搬

判据可以机械执行：**docstring 里有没有"不要 / 必须 / 否则会"这类指向"改动后果"的祈使句。**
有 → B；只有"之前……所以……"的叙述 → C。

## Q2：能不能放在外面？

**能。但有一条硬约束，违反它搬 = 删：**

> **搬出去的东西必须有机制保证被读到。**

本项目现在是**零机制**（无 doctest、无 Sphinx、无 `__doc__` 消费者）。所以直接搬走 C 和 D，等于把它们丢进一个没人打开的目录。

正确的做法不是"搬"，是**分流 + 留锚点**：

```
代码里（2–4 行）：  这个函数做什么 + 一条最致命的坑 + 详见 docs/adr/xxx.md
docs 里（完整）：   为什么这么设计、试过什么不行、实测数字、论文出处
```

**留锚点这一句不能省。** 它不是形式——它是"从代码到文档"的唯一指针。没有它，半年后没人知道 `docs/adr/` 里有对应记录。

## Q3：总结成一张表

| 类型 | 现在有多少 | 归宿 | 缩成几行 | 判据 |
|---|---|---|---|---|
| **A 契约** | 41 行（0.9%） | **代码内** | 保持 | 有 `Args/Returns/Raises` |
| **B 就地约束** | 唯一必须留的 | **代码内** | **≤3 行** | 有祈使句 + 后果 |
| **C 设计理由** | 大头 | **`docs/adr/`** | 代码内留 1 行 + 锚点 | 只有叙述，无祈使 |
| **D 证据数字** | 830 + 883 行（可重叠） | **`docs/` 或论文附录** | 代码内留锚点 | 有 arXiv 号 / 实测值 |

# 三、账：docstring 到底算不算数

**这里必须先说清一件事，否则会重演"看起来降了其实没降"。**

查 `src/domain/kmetric.py:35 lines_nb_code()`：

```python
if tok.type == tokenize.STRING:
    # 独占一条语句的字符串（docstring / 裸字符串）不算代码
    string_lines.update(range(start, end + 1))
...
return len(code_lines - string_lines)
```

**K 的主口径 `K_lines_nb` 明确把 docstring 排除在外。** 所以：

| 目标 | 搬 docstring 有用吗 |
|---|---|
| 降 **K**（项目自己的判定口径） | ❌ **完全无效，一行都不算** |
| 降**物理行**（"代码量"的通俗说法） | ✅ 有效，**但那是搬家，不是简化** |

**两个分母不能混用。** 上一轮我用的 19,510（docstring + 净代码）是后者，得先说清楚。

三种口径都列出来，选一个写死在验收里：

| 口径 | 行数 | 10% 目标 | 含 docstring |
|---|---|---|---|
| A 全部物理行 | 25,994 | 2,599 | 是 |
| B 非测试物理行 | 15,939 | 1,594 | 是 |
| C 非测试净代码 + docstring | 12,479 | 1,248 | 是 |
| **D 净代码（= K 的同族口径）** | **15,011** | **1,501** | **否** |
| **E 非测试净代码** | **9,144** | **914** | **否** |

**建议用 D 或 E。** 理由：它和 K 同族，不会出现"K 没降但代码量降了"的自相矛盾；docstring 单独报一个数，不计入分子分母。

## 四类的实际构成（实测）

| 类 | 文件 | 物理行 | 空行 | 注释 | docstring | **净代码** |
|---|---|---|---|---|---|---|
| test | 65 | 10,055 | 2,677 | 347 | 1,164 | 5,867 |
| infra | 55 | 8,002 | 1,385 | 321 | 1,713 | 4,583 |
| **scaffold** | **18** | **4,071** | 659 | 250 | 830 | **2,332** |
| **tool** | **15** | **3,866** | 622 | 223 | 792 | **2,229** |
| 合计 | 153 | 25,994 | 5,343 | 1,141 | 4,499 | 15,011 |

## 4.2 唯一挡路的一处：反向依赖

依赖检查结果：

```
✗ src/usecases/rewriter.py          ← 归为「工具本体」
    → src/usecases/inspector.py     ← 归为「脚手架」
    → src/usecases/planner.py       ← 归为「脚手架」
```

`rewriter.py:39-40` 只 import 了 4 个符号：

```python
from .inspector import LLMClient, _extract_json
from .planner import ALLOWED_FILES, TaskCard
```

**这 4 个都不是脚手架的"业务逻辑"，是两处错放的基础设施：**

| 符号 | 行数 | 本质 | 该在哪 |
|---|---|---|---|
| `LLMClient` | 5 | LLM 客户端 | `adapters/` |
| `_extract_json` | 18 | 通用工具 | `adapters/` 或 `domain/` |
| `TaskCard` | 22 | 共享数据类 | `domain/types.py` |
| `ALLOWED_FILES` | 常量 | **安全白名单** | `domain/`（它出现在 planner 里本身就不对） |

**修法：下沉，不是解开。** 把这 4 个搬到共用层，两边都从共用层 import。

⚠ **必须保留 re-export**：`TaskCard` 被 5 个测试文件 import、`ALLOWED_FILES` 被 `test_planner.py` import。直接改路径会破 B3 契约门。正确写法是在 `planner.py` 里留 `from src.domain.types import TaskCard  # re-export`。

**成本：移动约 45 行 + 改 3 处 import。这是方案 A 唯一的真改动。**

## 4.3 连带影响：cli.py 和测试

### cli.py 会缩，但要一起动

`cli.py` 1,219 行里有 **251 行**是脚手架的入口（`cmd_run_m0` / `cmd_prune_round` / `cmd_calib` / `cmd_sensitivity`）。

剥离脚手架 → 这 4 个子命令要跟着走。**但 `cli.py` 仍 >800 行**（1,219 − 251 = 968），所以 §B4 结构门还不会过。**方案 A 解决"代码量"，不解决"文件超长"——那需要另外拆包。**

### 测试：7 个跟走，49 个要拆

| 类型 | 文件 | 行数 | 处理 |
|---|---|---|---|
| `scaffold-only` | 7 | 1,014 | 跟着走 |
| `tool-only` | 9 | 1,223 | 留下 |
| **`mixed`** | **49** | **7,818** | **要逐个看，拆成"测工具的留下、测脚手架的跟走"** |

（`scaffold-only` 明细：`test_planner` 325 / `test_kpi` 175 / `test_explore` 150 / `test_report` 105 / `test_run_lineage` 101 / `test_contract_check` 89 / `test_rollback` 69）

**49 个 mixed 是方案 A 最大的隐性成本。** 不做这一步，剥离后会出现"测试还在跑，但测的东西已经不在这个包里"——比不剥更糟。

## 4.4 执行顺序（不可换）

```
第 0 步  存基线：覆盖率的行覆盖数据 + 违规数（scan_violations.py --save）
第 1 步  下沉 4 个符号（LLMClient / _extract_json / TaskCard / ALLOWED_FILES）+ 留 re-export
         → 跑全测试，必须全绿。此时还没搬任何文件
第 2 步  复检依赖：再跑一次反向依赖扫描，必须为空的
第 3 步  建新包（如 src_experiment/），先只搬 3 个文件做验证
         → 跑全测试 + 比覆盖率，确认没掉
第 4 步  搬剩下 15 个 + 7 个 scaffold-only 测试
第 5 步  处理 49 个 mixed 测试
第 6 步  报账：净代码 25,994→，违规数 3→，覆盖率不降
```

**第 1 步必须在第 3 步之前。** 先搬后修依赖 = 你会在一个本来就循环引用的状态下搬，出错分不清是搬错还是依赖错。

## 4.5 三个风险，先说清

**① 这不是"简化"，是"分家"。**
剥完之后，**代码总行数一点没少**，只是不再算作"工具"的一部分。如果论文里写"工具代码量降 15.7%"，必须同时写"实验框架独立成包"——否则是选择性报数。

**② 会失去"代码与实验同仓"这个便利。**
可以在同一仓库内分目录（monorepo），但 `python -m src.cli run-m0` 这类命令的路径会变，**所有历史实验记录里的命令都失效**。要么保留 shim，要么接受断代。

**③ 剥离后 `run_m0` 的复现性要重新验一遍。**
"可复现"是本课题的验收项。搬目录后 import 路径全部变化，**必须跑一次端到端实验，确认数据能复现**，而不是"测试过了"。

# 五、如果目标是"工具本身变简单"

方案 A 把工具从 25,994 行降到约 21,900 行（物理行）。但工具本体仍然只有 **3,866 行**（tool）+ 8,002 行（infra）。

**infra 里最大的是 `cli.py` 1,219 行**，其余是 adapters 和数据结构，都在 100–400 行区间——没有第二块可剥的"脚手架"。

所以方案 A 之后，**想继续降只有三条路，收益都很小**：

| 路 | 可减 | 说明 |
|---|---|---|
| docstring 分流（C + D 类搬 docs） | ~1,500 行 | 只降物理行，**不降 K** |
| 死代码 + 逻辑重复 | **64 行** | 天花板已经量过 |
| R1–R20 改写算子 | ~30 行 | 已实测，库里没有"100 个 if" |

**加起来不到 1,600 行，而且都不降 K。**

**这就是必须说清的一条：想让工具"真的更简单"，方案 A 是唯一有量的一步；再往后就不是减行数能解决的了，得改设计。**
