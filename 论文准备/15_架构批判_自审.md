# 架构自审：`exp` 的十一处问题

2026-11-01 ｜ 对象：`14_代码架构_exp.md`。写法：**先批判，再给修法**；每条标"证据"与"后果"，能证伪的才写。

---

## 〇、一句话结论

> **契约层（`contracts.py`）站得住；语义层有三处硬伤**：
> ① 判定器在纯删除流程里**没有区分力**；② **演化循环整体缺失**，`gate` 没有调用者；
> ③ 组件切分由适配器自报，**K 不可比**。
> 另外七条是"能跑但会难看"的问题，一条是"架构超配"。

**根因不在架构，在需求**：`14` 同时要两样东西——一个**演化器**（G4：接受准则、帕累托、δ）和一个**删除验证器**（G3：逐组件删测、三态）。
这两者的判定语义不同，我把它们塞进了同一个 `gate`。

## 二、三处致命

### 致命 1：判定器在纯删除流程里没有区分力

**现象**：我的 `gate` 继承 RRSI 的形态——"给一个候选，判它该不该被接受"。判据是 K 硬否决 + δ 双地板 + 三维支配。

**推演**：把删测算一遍。删掉一个组件，K **必然下降**（少了一段源码），S 要么不掉（=删除）、要么掉（=保留）。
那么 `judge` 遇到的每个候选都是 `ΔK < 0`。

> `if ΔK > δ_K: reject` —— **永不触发**。
> 三维支配 `if ΔS ≤ 0 and ΔK > 0: reject` —— **永不触发**。

`14` 的 G4 判据写着"构造 S+0.5 / K+30% 的假候选，判定必须拒"。
**这个假候选在我们的真实流程里根本不会出现**——因为工具只会删，不会加。

**后果**：G4 的测试只能靠手工构造的假数据通过，跑不出真实数据。论文里"K 可单独否决"这句话，
会被审稿人问一句："你的流程里 K 什么时候涨过？"

**根因**：判定的对象错了。删测场景下要判的不是"这个候选值不值得接受"，而是**"这次删除是否可信"**——
即删掉之后 S 不掉，是因为它真的无用，还是因为我的测试没测出来（n 不够 / 判分不稳 / 变体悄悄失效）。

**修法**：
- `gate` 拆成两个判据，语义分开：
  - `judge_delete_trust(base, cand, delta, n) -> {trusted_delete | kept | undecidable}` —— 删测用
  - `judge_candidate(cand, incumbent, delta) -> Verdict` —— 演化用（K 硬否决在这里才成立）
- 论文里如实写 G4 的作用面：**K 否决在演化臂上生效，在删测臂上不触发**；
  删测臂的证据是"K 降 + S 不降 + 有 CI"，不是"否决了一个涨 K 的候选"。

---

### 致命 2：演化循环缺失

**现象**：架构里有 `runner.py`（一次 run = 一次评测）、`counterfactual.py`（一次删测）、`gate.py`（判定），
但**没有任何模块负责"多轮迭代"**——没有 propose、没有 incumbent 更新、没有谱系落盘。

**证据**：`16` 的 §5.1 数据流是 `for seed: for task: rollout`，是一个**评测器**的形状。
而 `10` 的 M3 要求"**至少 2 次独立演化**并报两次差异"，M4 要求"3 次独立演化 × 每次 3 次评测"。

**后果**：
- `gate` 写出来没有消费者（致命 1 的另一半）；
- A1 消融（"K 不作否决，只记账"）要对比两臂，但两臂都是"演化"产生的，而演化不存在；
- 十类字段里的第 9 类（谱系：candidate → parent → 接受/拒绝理由）无处产生。

**修法**：补 `evolve/` 模块，形态必须极简（不重造 RRSI）：

```
evolve/
  loop.py        # while t < T: 生成一个候选 → 评测 → 判定 → 更新 incumbent
  incumbent.py   # 只存"当前最好的那个 commit/目录 + 它的 S/C/K + 谱系"
  propose.py     # 候选从哪来：S2 之后只有一种——"删一个组件"
```

关键设计约束：**候选来源只有一条路（删组件）**，所以 `propose` 不需要 LLM，不需要 proposal network。
这正是"我们是删，不是改得更好"的落地。若将来要加"改"的候选，才需要 LLM。

---

### 致命 3：组件切分由适配器自报，K 不可比

**现象**：`AgentAdapter.components()` 返回组件清单，同时 `measure/split.py` 又有切分规则。
**两份真相**，且没规定谁说了算。

**推演**：写 Terminus-2 适配器时我把它切成 20 个组件，写 mini-swe-agent 时切成 3 个。
两边的"组件→K"分布能放同一张表吗？

> `10` 的 T1 要"6 个 agent 的组件→K 分布，一张表 + 一张堆叠柱图（**哪类组件最占体积**）"。

如果切分靠适配器作者的手艺，这张图量的是**我切得细不细**，不是**agent 臃肿在哪**。
更糟：删测的粒度也由它决定——"逐组件删"变成"逐我划的块删"。

**后果**：G2 的"可复算"打折（口径依赖人），T1 的结论不可信，删测表的"组件"列没有客观定义。

**修法**（这条必须硬性）：
- **切分只由 `split.py` 决定，适配器只提供"边界声明"**（哪些目录/文件属于哪一类），不提供组件列表；
- 边界声明写进 `manifest.json`，作为口径的一部分——**换边界 = 换口径 = 换一次实验**；
- `components()` 的签名改成 `boundaries() -> BoundarySpec`，组件由 `split(boundaries)` 派生；
- 加一条测试：同一份 harness，两个不同的人写边界（但按同一目录约定），切出的组件数必须相同。

## 三、四处重大

### 重大 4：`Session.exec(str)` 把有状态终端降维成无状态命令

**现象**：我的 `Session` 只有 `exec(cmd) / read / write`。

**证据**（已核对源码）：`external/repos/terminal-bench/terminal_bench/terminal/tmux_session.py` 的公开接口是
`send_keys`(:249) / `send_command`(:296) / `capture_pane`(:317) / `get_incremental_output`(:321) /
`is_session_alive`(:312) / `get_asciinema_timestamp`(:237) / `copy_to_container`(:384)——
Terminus-2 与环境的交互是**有状态的字节流**（发键 → 等 → 抓增量屏 → 判存活），
不是"执行一条命令拿 stdout"。其中 `get_incremental_output` 还得自己算"屏上哪些是新内容"。

**后果**：Terminus-2 适配器只有两条路：
① 在 `Session` 上模拟 tmux（把 `send_keys` 翻译成 `exec`）→ 行为不等价，抓屏时序全丢；
② 绕过 `Session` 直接持有 tmux 对象 → **G1 的"换 agent 不改主流程"破功**。

**修法**：`Session` 从"最小公倍数"改成**能力协商**：

```python
class Session(Protocol):
    def capabilities(self) -> frozenset[str]:      # {"shell","fs","tmux","browser","mcp"}
    def shell(self) -> Shell: ...                  # 有 shell 能力时才有
    def tmux(self) -> TmuxHandle: ...              # 有 tmux 能力时才有
    def fs(self) -> FileHandle: ...
```

适配器在 `prepare` 阶段声明 `requires: frozenset[str]`，不匹配就**立刻失败**并打印缺什么。
**失败得早，好过运行时静默降级**（这正是记忆里"静默降级"那条错误）。

### 重大 5：`step()` 在别人的 agent 上不可实现

**现象**：契约写的是 `step()` 单步推进，理由是超时/中断/失败签名。

**证据**（已核对源码）：mini-swe-agent 的入口是一个完整的 `run()` 循环；
Terminus-2 更直接——`terminus_2.py` 里有 `_run_agent_loop`(:523)，`perform_task`(:594) 只是它的薄封装，
循环内部还有 `_execute_commands`(:491)、`_summarize`(:230)、`_unwind_messages_to_free_tokens`(:205)。
我**没有钩子**能插进这个循环——要插就得重写它，而"自研 agent 框架"是非目标。

**后果**：实现时 `step()` 必然被实现成"跑完这一题"，契约名不副实。
更麻烦的是失败签名：我声称从"逐步观察"归一化，但实际上只能拿到 agent 自己吐的轨迹（格式各家不同）。

**修法**：
- 契约改成 `advance() -> AdvanceResult(done: bool)`，**粒度由 agent 决定**，不承诺单步；
- 失败签名不依赖"我们的观察"，而依赖**判分器的输出**（TB2 是 pytest 的失败断言，分类是混淆矩阵的错分样本）——
  这才是客观且跨 agent 一致的；
- 若某个 agent 确实暴露了 step 钩子（如 OpenHands 的 event stream），适配器可以自己映射成多次 `advance()`，
  但**契约不要求**。

### 重大 6：删除的引用闭合会让大量组件"删不掉"，缺第四态

**现象**：`mutate.py` 的三道门里，第二道是"删掉 symbol 后全仓无残留引用"。
若不满足，我写的是"拒绝或连带删"。

**推演**：Terminus-2 的 `execute_commands` 被 `perform_task` 调用。删它 → 引用残留 → 只能连带删调用点。
连带删调用点 → 控制流变了 → **这已经不是"删一个组件"，是"改结构"**，违反 R3（一次只改一处）。

**后果**：真实 agent 上"可单独删"的组件比例可能很低。删测表里 `undecidable` 会占大头，
而我的三态里**没有"删不掉"这一类**——"删不掉"和"不知道效果"是两件事，混在一起就是把工具缺陷说成实验结论。

**修法**：
- 三态扩四态：`keep / delete / undecidable / undeletable`；
- `undeletable` 必须带原因（`dep-broken` / `syntax-broken` / `smoke-failed`），且**不进分母**；
- 分层策略：删测只在"组件边界清晰"的 agent 上做（mini-swe-agent、自建分类 harness），
  框架型 agent（OpenHands）只做 K 测量 + 静态死组件；
- 论文里必须报一个数：**可删组件数 / 总组件数**——这个比例本身就是"agent 模块化程度"的度量，
  是可以写进论文的副产品，而不是需要遮住的缺陷。

### 重大 7：K 的"静态可算"是隐含假设

**现象**：我把 `measure/` 设计成纯离线，读源码算 K。

**证据**：但 agent 的一部分 harness **不在源码里以文本形式存在**：
- system prompt 可能是 `make_system_prompt()` 运行时拼的；
- tool schema 常常是**反射函数签名生成的**（源码里没有那段 JSON）；
- memory 是运行时累积的，不是一个文件。

**后果**：K 会系统性地**低估**这三类。而 `12` 明确写"六类组件：prompt / tools / middleware / memory / subagent / skills"——
工具这一类恰好最容易被低估。

**修法**：在 `MetricSpec` 里加一个显式字段 `coverage: {static: [...], excluded: [...]}`，
并在论文附录写死一句：

> K 只量**静态可枚举的交付物**。运行时生成的 prompt 与反射生成的 schema，
> 按其**生成代码**计入，不按运行时实例计入——否则 K 会随运行次数变化，失去可比性。

这不是缺陷修补，是**口径声明**。不声明，被问就答不上。

## 五、根因：需求文档的语义漂移

把 `14` 的两节并排看：

| `14` 的节 | 它假设的工具形态 | 判定的对象 | 候选从哪来 |
|---|---|---|---|
| **G3 删除** | **删除验证器**：逐组件删、真跑、三态 | "这次删除可信吗" | 穷举组件 |
| **G4 判定** | **演化器**：δ 地板、三维帕累托、接受准则、incumbent | "这个候选该不该接受" | 上一轮的最佳 + 变异 |

**这是两个不同的程序。** G4 的词汇（"地板 `S*−δ`"、"帕累托"、"incumbent"）全部来自 RRSI 的演化框架；
G3 的词汇（"逐组件删"、"三态"、"不可判"）来自删测验证。`14` 把它们并列写成"六个能力目标"，没有说清主从。

我上一版架构的错，是**照抄了 RRSI 的 `gate` 形态**去实现一个**删测工具**的判定。
形态没错，位置错了。

**必须先回答一个问题**（这也是我要问皓阳的）：

> 这个工具最终交付的是**一个删测验证器**（证明"这些组件删了不掉分"），
> 还是**一个演化器**（自己去找"能删什么"，跑 T 轮，产出 incumbent）？

答案不同，架构的重心不同：

| 答案 | 重心 | `gate` 的角色 | 工作量 |
|---|---|---|---|
| 删测验证器 | `remove/` + `report/` | 只判"删除可信度"，K 否决降为可选 | 小，S0–S2 就够 |
| 演化器 | `evolve/` + `judge/` | 核心，K 否决是主张 | 大，要补 M3/M4 的全部 |
| 两者都要 | 两个模块 + 两套判据 | 两条通道 | 最大，且论文要写清哪个是主贡献 |

## 六、如果只改三处

按投入产出排序：

1. **补 `evolve/` 或删掉 `gate` 的演化语义**（致命 1+2 一起解）。
   不补演化，就把 `gate` 改造成"删除可信度判定"，K 否决只作为消融臂存在。
   这一步决定整个工具是"论文的核心图"还是"论文的附录"。
2. **切分客观化**（致命 3）。改 `AgentAdapter.components()` → `boundaries()`，加一条"两人切分一致"的测试。
   这一步不做，T1 的表和 T2 的删测表都没有客观分母。
3. **`Session` 改能力协商 + 三态扩四态**（重大 4+6）。前者救 G1，后者救删测表。

---

## 七、我不打算改的三处（这些不是问题）

批判要有边界。以下三条我坚持原设计：

| 坚持 | 理由 |
|---|---|
| **另起 `exp/` 包，复用靠 `reuse.py` 单点** | `src/` 的 614 个测试锁死了旧口径；`reuse.py` 单点引用避免两份实现分叉（`prototype/simplify` 已踩过） |
| **K 离线算，永不进 rollout 循环** | K 一旦依赖运行，就会随机器、tokenizer、上下文长度漂移，不再可比。这个性质是整个"可复算"的地基 |
| **删除必须物化，运行时禁用不算删** | 禁用不改源码 → K 不降 → 删测表会出现"删了 15 个组件、K 没变"的自相矛盾 |

---

## 八、这套架构怎么被否证

三条否证条件，任意一条成立就说明架构错了：

1. 加第三个 agent 要改 `run/` → `AgentAdapter` 少给了东西（大概率是 `Session` 的能力粒度）。
2. 删测表里 `undecidable` 恒为 0 → n 的约束没进代码，三态写成了两态。
3. **A1 消融（K 只记账）与主臂结论一致** → K 在判定里根本没起作用，`14` 的整个主张塌掉。
